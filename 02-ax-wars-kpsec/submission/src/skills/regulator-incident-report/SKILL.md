# 금감원 사고보고서 생성기 (별지 제2호서식)

전산장애 발생 시 담당자(CISO 조직/비상연락 담당자)가 **EFARS에 제출할 사고보고서 초안**을 만든다. 규정 근거는 `reference/efars-rules.md` 참조.

## 경계 (반드시 지킬 것)
- 이 스킬은 **문서 초안 생성까지만** 한다. **EFARS 자동 제출은 하지 않는다**(공개 API 없음·보안격리망). 제출은 사람이 한다.
- 숫자·사실을 **지어내지 않는다.** 미입력 항목은 `(미입력)`/`파악 중`으로 두고 보완을 요청한다.

## 법령 최신성 가드레일 (실행 전 1회, 필수)
이 스킬의 보고 대상 기준(30분 / 10분+1만명)·시한(24시간 / 2개월 / 매6개월)은 **전자금융감독규정 시행세칙 제7조의4**에 근거한다. 규정은 개정되므로, 스크립트 실행 전 **`korean-law` MCP로 현행 조문을 1회 교차확인**한다:
1. `korean-law` MCP(연결돼 있으면)로 **전자금융감독규정시행세칙**을 검색(`search_admin_rule`)해 [현행] 버전을 확인하고, 제7조의4(정보기술부문 사고보고) 본문을 조회(`get_admin_rule`).
2. `reference/efars-rules.md`의 기준(30분/10분·1만명, 24h/2월/6월, 별지 제2호서식 항목)과 **대조**한다.
3. **달라졌으면**: 변경 내용을 사용자에게 먼저 알리고, `scripts/generate_fss_report.py`의 판정 임계·시한과 `reference/efars-rules.md`를 갱신한 뒤 진행한다.
4. MCP가 없거나 조회 실패 시: 기존 기준으로 진행하되 **"법령 최신성 미검증"** 을 사용자에게 고지한다.
- (동일 원칙: 개인정보 유출은 privacy-breach-filing가 개인정보보호법 시행령 제40조를 같은 방식으로 확인.)

## 입력: incident.json
- 공통 데이터 모델 `shared/incident.schema.json` 구조의 `incident.json`을 입력으로 받는다.
- 사용자가 파일 경로를 주면 그대로 사용한다.
- **자동 사전 검증**: 스크립트 실행 시 `shared/scripts/validate_incident.py`로 스키마 enum(사고유형·세부유형 등)·필수필드를 **자동 점검**하고, 오류가 있으면 산출물 생성을 **중단**한다(`--no-validate`로 우회). `run_all_skills.py`도 맨 앞에서 1회 검증한다.

### incident.json이 없으면 — AskUserQuestion 인테이크 (필수)
자유서술로 묻지 말고 **반드시 AskUserQuestion 도구로 한 문항씩 구조화해 묻는다.** 선택지에 없는 값은 "Other"로 직접 입력. 목표는 **이 사고가 14개 법적 케이스(→ `04_법적경우의수_분석.md`) 중 무엇인지 가려내는 것**이다.

#### ⛔ 철칙 — 모르면 추측 금지, 반드시 물어라
- **판정을 가르는 값**(사고유형 대분류 · 지연·중단 시간 · 영향 이용자수 · 개인정보/신용정보 유출 여부 · (사기)사고금액)은 **임의로 추정하지 않는다.**
- 모르면 각 문항의 **'파악 중/미상'** 옵션을 고르게 한다. 미상이면 incident.json에 **null**로 두고, 스크립트가 "미상 + 임계 재판정 필요"로 처리한다.
- **구간(버킷) 중앙값으로 법정 임계(30분·1만명·1억·3억)를 넘겨짚지 말 것** — 임계 부근이면 반드시 정확값 또는 "임계 이상/미만 확실" 여부를 물어라.
- 정보가 부족하면 스크립트를 돌리기 전에 AskUserQuestion으로 **추가 문항을 던져** 채운다.

#### Round 1 — 대분류·병행신고 (최상위 분기, 필수)
1. **사고 유형 대분류** (header: `사고유형`) — 전산장애(서비스 지연·중단) / 침해사고(해킹·악성코드·DDoS·정보유출) / 전자금융사기(피싱·명의도용) / **파악 중**  ← 나머지 질문의 분기점. 모르면 '파악 중'.
2. **보고 단계** (header: `보고단계`) — 최초보고(기본) / 중간보고 / 종결보고
3. **최초 인지 주체** (header: `인지주체`) — 금융회사(모니터링·APM) / 고객(민원인) / 기타
4. **개인정보·신용정보 유출 동반** (header: `개인정보`) — 없음 / 개인정보 유출 / 신용정보(계좌·거래내역) 포함 / 둘 다 / 파악 중  ← privacy-breach·정보통신망법 KISA 트리거

#### Round 2 — Round 1의 '사고유형'에 따라 분기
**(A) 전산장애면:**
1. **세부유형** (header: `세부유형`) — 업무처리 프로그램 오류 / 시스템 장애 / 시설·설비 장애 / 외부요인(클라우드·통신·제휴·외부브로커) / 미정(파악 중)
2. **지연·중단 시간** (header: `중단시간`) — 정확한 분 직접 입력(권장) / 30분 이상 확실 / 10~30분 / 10분 미만 / 미상  *(임계 30분·10분이 핵심)*
3. **영향 이용자수** (header: `영향규모`) — 정확한 수 직접 입력(권장) / 1만명 이상 확실 / 1만명 미만 확실 / 미상  *(임계 1만명이 핵심 — 미상이면 null)*
4. **영향 서비스/시장** (header: `영향서비스`, multiSelect) — 해외주식 주문·체결 / 국내주식 주문·체결 / 앱 로그인·인증 / 입출금·이체
   - (세부유형=외부요인이면 후속) **외부 원인 회사** (header: `외부업체`) — DriveWealth / Koscom / 클라우드 업체 / 기타
   - (해당되면 후속) **보고 제외사유** (header: `제외사유`) — 해당없음 / 1개 영업점에만 국한 / 단순 정보제공 공개 웹서버

**(B) 침해사고면:**
1. **공격 대상** (header: `공격대상`) — 내부망 시스템 / DMZ구간 시스템 / 기타 / 미상
2. **공격 방법** (header: `공격방법`) — 악성코드(랜섬·웹쉘) / 서비스거부(DDoS) / 보안취약점 해킹 / 무단접속·조작 / 공급망 침해 / 미상
3. **공격 피해** (header: `공격피해`, multiSelect) — 시스템·서비스 중단 / 정보유출 / 중요정보 조작 / 금전적 손실 / 미상
4. (Round1 개인정보=유출/둘다면 후속) **유출 항목·규모** — 유출 항목(성명/주민번호/계좌번호/거래내역 등, 한 문항씩)과 정보주체 수(정확 수 우선)를 물어 privacy-breach로 넘긴다.

**(C) 전자금융사기면:**
1. **세부 사고유형** (header: `사기유형`) — 피싱/파밍(인터넷) / (모바일) / (텔레뱅킹) / 전자상거래·매체 위변조 / 신종 / 원인미정
2. **사고금액** (header: `사고금액`) — 정확한 금액 직접 입력(권장) / 3억원 이상 / 100만원~3억원 / 100만원 미만 / 미상  *(임계 100만·3억이 보고제외·일괄보고를 가름)*

#### Round 3 — 정확값 필요 항목만 짧게 텍스트로
① 사고 인지/발생 시각(+복구 시 종료 시각) ② 사고 발생 시스템명 ③ 사고 내용(현상·결과 1~2줄). (시각은 카운트다운 정확도를 위해 텍스트로 정확히 받는다.)

#### 매핑 (임시 incident.json 저장 → 스크립트 실행)
- 사고유형→`classification.incident_category`; 세부유형→`failure_subtype`; 외부요인→`cause.external_factor=true`+`responsible_company`.
- 중단시간→`impact.disruption_minutes`(**정확값만; '30분 이상 확실'=경계 판정용 최소값 표기, 미상=null**); 영향규모→`impact.affected_users_count`(**정확값 또는 null; 구간 중앙값 금지**).
- 개인정보→`security.personal_data_affected`/`info_type`; 침해 공격정보→`security.attack_target`/`attack_method`/`attack_damage`.
- 사기 사고금액→`impact.incident_amount_krw`(정확값 또는 null).
- 제외사유→`impact.single_branch_only`/`public_webserver_only`.
- 값이 미상(null)이면 보고서·PDF는 '(미상)'로 두고, 판정에 **"임계 재판정 필요"** 경고가 자동으로 붙는다. 담당자에게 정확값 보완을 요청한다.

## 실행 절차
1. **보고 단계 확인**: 최초(initial)/중간(interim)/종결(final) 중 무엇인지 사용자에게 확인. 기본은 initial.
2. **스크립트 실행** (결정적 판정·시한·매핑):
   ```bash
   python3 scripts/generate_fss_report.py <incident.json 경로> --stage <initial|interim|final> [--now <ISO시각>]
   ```
   - `--now`는 시한 카운트다운 기준 현재시각. 데모/특정시점 검증이 아니면 생략(실제 현재시각 사용).
   - **산출물은 항상 `.md` 파일로 자동 저장**된다: `<incident.json 폴더>/out/<id>_금감원_<단계>보고.md` (담당자·유관자가 바로 열람/팀 공유). 저장 경로는 `--out`으로 변경, 저장 생략은 `--stdout-only`.
   - 저장된 파일 경로를 사용자에게 반드시 알린다.
3. **결과 검토·보강 (모델의 판단 역할)**:
   - **보고 대상 판정**을 사용자에게 먼저 알린다. 비대상/제외면 그 이유를 명확히.
   - **누락 항목**이 있으면 사용자에게 구체적으로 질문해 채운 뒤 재실행.
   - 스크립트가 만든 `사고내용`·`사고원인` 서술이 빈약하면 incident.json 사실 범위 내에서 **문장을 다듬는다**(새 사실 추가 금지).
   - `사고원인`이 '파악 중'이면 최초보고는 그대로 제출 가능함을 알리고, 중간·종결보고 전 확정이 필요함을 안내.
   - 외부요인 장애면 **사고유형='외부요인으로 인한 장애'**, 파급영향의 **'사고 원인 회사명'**(예: DriveWealth)이 채워졌는지 확인.
4. **출력 전달**: 보고서는 **자기완결형**(담당자·유관자가 이 문서만 읽어도 파악 가능)으로 다음을 포함한다 — ▲문서 생성시각(초단위)·상태 메타 ▲한눈 요약(Executive Summary) ▲보고 대상 판정 ▲보고 시한(생성시각 기준 남은 시간, 초단위) ▲사고 타임라인 ▲영향 상세 ▲원인 상세 ▲대응 현황/재발방지 ▲필수항목 점검 & 다음 조치 ▲[제출물 A] EFARS 필드블록 ▲[제출물 B] 첨부용 별지 제2호서식. 저장 경로와 함께 사용자에게 전달한다.
5. **(선택) 공식 서식 PDF 생성**: 사용자가 "PDF", "공식 서식", "별지 서식으로", "붙임 문서"를 요청하면 원본 **별지 제2호서식과 동일 포맷의 PDF**를 만든다.
   ```bash
   python3 scripts/generate_fss_pdf.py <incident.json> --stage <initial|interim|final> [--html-only]
   ```
   - incident.json을 입력으로 **①표지(공문) + ②별첨1(사고내용)**을 원본 서식 그대로 재현. 표지 첫 페이지에 **회사 정식 법인명**(`company.json`의 `legal_name` = "카카오페이증권 주식회사")과 서명란(`representative_title` 대표이사)이 들어간다.
   - 변환은 시스템 **헤드리스 브라우저(Chrome/Edge)**로 HTML→PDF. 저장: `<incident 폴더>/out/<id>_금감원_별지제2호서식.pdf` (+ 동명 `.html`). 브라우저가 없으면 HTML만 저장하고 "브라우저에서 PDF로 인쇄" 안내(→ `--html-only`와 동일).
   - 사고유형 체크박스는 `classification`·`security` 값으로 자동 체크(전산장애 세부/침해 공격대상·방법·피해/사기 세부). 서식 구조·매핑은 `reference/efars-rules.md` 참조.
   - **주의**: 서명란 대표이사 성명은 시점별로 바뀌므로 `company.json`의 `representative_name`이 비어 있으면 공란으로 둔다(임의 기재 금지). 제출 전 담당자가 실제 명의·문서번호·수신처를 확정한다.
   - **정합성 가드레일**: md 보고서와 PDF는 **같은 incident.json**에서 생성되므로 사실이 어긋나면 안 된다. `shared/scripts/verify_fss_consistency.py <incident.json>`로 **incident.json ↔ md ↔ PDF(체크박스)** 3자 일치와 스키마 enum을 자동 검증하고, 미입력·미상 항목을 나열한다(불일치 시 exit 1). `run_all_skills.py`는 이 검증을 마지막에 자동 실행한다.
   - **PDF 체크박스가 비어 있는 이유**: ①해당 사고유형이 아닌 열(침해·사기 열 전체)과 ②원인·규모가 '미정/미상'인 항목은 **정상적으로 공란**이다(원본 서식도 담당자가 해당 열만 체크). 공란=오류가 아니라 '해당없음 또는 미상'이며, 미상 항목은 위 검증기가 별도로 나열해 보완을 유도한다.

## 단계별 주의
- **최초보고**: 24시간 시한이 핵심. 원인 미확정이어도 알려진 사실로 우선 제출. 시한 임박/경과 경고를 강조.
- **중간보고**: 대응 타임라인(`timeline.events`)과 진행상황을 반영.
- **종결보고**: `timeline.resolved_at`·`measures`(재발방지)·배상조치(있으면 `compensation`)가 채워져야 한다. 누락 시 보완 요청.

## 데이터 모델 변경
구현 중 incident.json에 필드 추가/수정이 필요하면 `shared/incident.schema.json`과 `scripts/generate_fss_report.py`를 함께 갱신하고 사용자에게 알린다.
