# 개인정보·신용정보 유출 통지·신고 생성기

침해사고로 개인정보/신용정보가 유출됐을 때, **전산장애 금감원 보고(스킬1)와 별개로** 필요한 통지·신고 산출물을 만든다.

## 경계
- **산출물 생성까지만.** 실제 통지·신고는 사람이 한다.
- 활성 조건: `security.personal_data_affected == true`. 아니면 '해당없음'으로 종료.
- 신고 임계·전문기관 세부요건은 **최신 법령으로 확인**(법제처 MCP 활용 권장).

## 입력
- `incident.json`의 `security`: `personal_data_affected`, `info_type`(개인정보/신용정보/둘 다), `leaked_items[]`, `leaked_count`. + `detection.detected_at`(72시간 기산), `cause.root_cause`, `handling`, `measures`.
- **자동 사전 검증**: 스크립트 실행 시 enum(info_type 등)·필수필드를 자동 점검하고 오류 시 중단(`--no-validate`로 우회). `run_all_skills.py`도 맨 앞에서 1회 검증.

## 실행
```bash
python3 scripts/gen_privacy_breach_report.py <incident.json> [--now <ISO>] [--out <경로>] [--stdout-only]
```

## 산출물
- **A. 정보주체 통지문**: 개인정보보호법 제34조 5대 포함사항(① 유출항목 ② 시점·경위 ③ 정보주체 조치 ④ 대응·피해구제 ⑤ 신고·상담처).
- **B. 감독기관 신고서 초안**: 근거법·인지일시·유출항목·규모·경위·조치·재발방지.
- **72시간 신고 시한** 카운트다운(개인정보보호법) + **신용정보 포함 시 신용정보법 제39조의4 금융위·금감원 신고를 개인정보위(72h)와 분리 트랙(이원 신고)으로 명시**(1만명↑면 대상 가능성↑) + **침해사고면 정보통신망법 §48조의3 KISA 24h 신고 교차참조**(regulator-incident-report 「1-1」와 동일 근거, 서로 갈음 안 됨).
- 출력은 항상 `<incident 폴더>/out/<id>_개인정보유출신고.md`로 **자동 저장**된다(경로는 `--out`으로 덮어쓰기, 저장 생략은 `--stdout-only`). 저장 경로를 사용자에게 보고하라.

## 모델 역할
- `leaked_items`·`leaked_count`가 비면 반드시 확인(유출 항목·규모는 통지·신고의 핵심).
- 유출 항목(`leaked_items`)·정보 종류(`info_type`)는 **AskUserQuestion으로 한 문항씩** 받아라(free-text 지양).
- **유출 규모(`leaked_count`)는 구간 선택이 아니라 '정확한 수 직접 입력'을 1번(최우선) 옵션으로 제시**하고, "정확한 정보주체 수를 입력해야 신고서·피해대응이 정확하다"는 문구를 문항에 넣어라. (참고: '1천명'은 개인정보보호법 시행령 제40조1항1호의 신고 임계로 규제적 의미가 있으나, **2호(민감·고유식별정보)·3호(외부 침해)는 규모와 무관하게 신고 대상**이므로 구간보다 정확 수치가 중요.)
- `info_type`에 따라 근거법 정확히: 계좌번호·거래내역 등 **금융거래정보가 포함되면 '둘 다'(개인정보보호법+신용정보법)** 로 잡아 신용정보법 병행 신고를 안내.
- 스크립트가 시행령 제40조 1/2/3호 신고 대상 판정을 자동 표기한다 — 결과를 사용자에게 근거와 함께 설명.
- **신고 임계·기한은 `korean-law` MCP로 개인정보보호법 제34조·시행령 제40조 [현행] 조문을 교차확인**하고, 개정이 의심되면 사용자에게 알려라.

## 데이터 모델
유출 관련 새 필드가 필요하면 `shared/incident.schema.json`의 `security`와 스크립트를 함께 갱신.
