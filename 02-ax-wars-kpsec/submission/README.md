# kakaopaysec-incident-response — 카카오페이증권 전자금융사고 대응 문서 자동화

전자금융사고(전산장애·침해사고·전자금융사기) 발생 직후, **담당자가 규제 시한 안에 만들어야 하는 보고·공지·신고 문서를 사실 입력 한 번으로 자동 생성**하는 Codex 플러그인. 인프라 복구나 감독원 시스템 자동제출은 하지 않음 — **제출 직전 단계의 완성 문서**를 만들어 담당자의 백지·시한 압박을 없앰.

---

## 심사 5문항

### 1. 무엇을, 누가, 어떤 상황에서 쓰나요? *(800자 이내)*
카카오페이증권의 IT사고 대응 담당자가 전자금융사고(전산장애·침해사고·전자금융사기) 발생 직후, 사고 사실을 한 번 입력하면 **금감원 사고보고서(별지 제2호서식·PDF)·고객 장애공지·경영진/이사회 보고·개인정보 유출 신고·대응 시한 대시보드**를 자동 생성하는 Codex 플러그인이다.

**누가** — CISO 조직·비상연락 담당자(규제 보고), 컴플라이언스(유출 신고·이사회 상정), 고객대응(공지)이 함께 쓴다. **어떤 상황** — MTS 먹통·체결지연·해킹·정보유출이 터져 인지 후 **24시간(금감원)·72시간(유출)** 시한이 도는 야간·주말 소수 인력 대응 상황이다. **어디서 막히나** — ① "이게 보고 대상인가"를 30분/10분+1만명 같은 임계로 규정에서 찾아 판단해야 하고, ② "침해면 KISA에도 신고해야 하나·이사회까지 올려야 하나"처럼 금감원 보고로 갈음되지 않는 병행 신고를 놓치기 쉬우며, ③ 별지 제2호서식·정보주체 통지문·이사회 보고서를 백지에서 동시에 작성해야 한다. 이 반복 작업에서 공지 시점 불일치·원인 누락·보고 지연이 생긴다. 플러그인은 진입점 스킬이 4문항으로 사고를 분류해 시한 기준 대응 순서를 안내하고, 각 산출물의 판정과 초안을 **'제출 직전 단계'까지** 자동으로 끌어올린다(실제 제출·발송·복구는 사람 몫).

### 2. 왜 이 문제를 선택했나요? *(800자 이내)*
카카오페이증권은 MTS 전산장애가 **2022년 4건→2023년 9→2024년 11→2025년 13건으로 4년 연속 증가**(누계 42건)했고, 조사대상 12개 증권사 중 유일하게 매년 늘었으며 2026년 1분기 5건으로 단독 최다다. IT투자는 연평균 약 **395억원**으로 장애 0건인 미래에셋(1,585억)의 1/4 수준이다. 즉 사고는 구조적으로 계속 난다. 예방(인프라)은 대규모 투자·시간이 필요하지만, **'터진 뒤 규제 대응'은 공개 규정만으로 정확히 표준화**할 수 있어 자동화 가치가 즉시 크다 — 그래서 예방이 아닌 대응 산출물을 문제로 골랐다.

실제로 어디서 막히나: **직원(담당자)**은 24h/72h 시한 속에서 규정 해석과 서식 작성을 동시에 해야 해 백지·시간 압박에 걸린다. **고객**은 '정상화 공지 후에도 미복구'(2025년 10월 한 달 4회 먹통)로 매매 기회를 놓치고 신뢰가 떨어진다. **감독당국**은 반복 장애에 2026년 4월 IT부문 현장점검에 착수했다. 산업 전반도 핀테크 증권사 장애가 급증(토스증권도 42건 공동 최다)해 대응 표준화 수요가 크다.

### 3. 플러그인은 어떻게 작동하나요? *(1000자 이내)*
**절차** — 진입점 스킬 `incident-response`가 사고유형·복구여부·개인정보 동반·규모 4문항(AskUserQuestion)으로 사고를 분류하고, 단일 사실 원장 `incident.json`을 만든 뒤, **시한 기준 조건부 순서**로 5개 스킬을 호출한다: 고객 실시간공지=즉시, 금감원 보고=24h, 병행신고=조건부, 이사회 보고=중대 시, 복구공지·종결·보상=복구 후, 대시보드=상시.

**지식·판단 기준** — 판정을 법 조문 단위로 코드화했다. 금감원 보고 대상=지연·중단 30분 이상 또는 10분+이용자 1만명(시행세칙 제7조의4), 제외=1개 영업점·공개웹서버·사기 100만원 미만·3억원 미만 일괄, 유출 신고=1천명/민감·고유식별/외부침해 3근거(개인정보보호법 시행령 제40조), 이사회 중대성=필수사유(침해·개인정보) 또는 가중요인 2개↑, 병행 신고=정보통신망법 제48조의3 KISA 24h·개인정보 72h·신용정보법 제39조의4. 임계값은 `company.json`으로 외부화해 회사 정책에 맞게 조정할 수 있다.

**정보가 부족하거나 안 풀릴 때** — '추측 금지'가 원칙이다. 값이 불확실하면 '파악 중/미상'으로 두고 `incident.json`에 `null`을 저장하며, 스크립트가 **"임계 재판정 필요" 경고**를 붙인다(구간 중앙값으로 30분·1만명 임계를 넘겨짚지 않는다). 실행 전 `validate_incident`가 enum·필수필드를 검증해 오류면 생성을 **중단**하고, 산출물은 `verify_fss_consistency`가 incident.json↔md↔PDF 체크박스 3자 일치를 검증한다. 헤드리스 브라우저가 없으면 PDF 대신 HTML을 저장하고 '인쇄로 PDF' 안내로 대체한다(graceful). 복구 전(`resolved_at` 미확정)이면 '정상화' 공지와 종결보고를 잠근다. 경계로, 탐지·복구·감독원 실제 제출·공지 발송·보상액 산정은 사람/사내 시스템의 몫이다. (동일 내용은 zip의 `README.md`에도 수록.)

### 4. AI를 어떻게 썼나요? *(800자 이내)*
**AI에 맡긴 것** — 멀티에이전트로 공개자료(국정감사·언론·법제처)를 병렬 리서치·교차검증(‘42건’이 개별 사건이 아니라 금감원 제출 연간 집계 누적임을 규명), 별지 제2호서식 PDF 재현, 단일 매핑 모듈·검증기 반복 리팩터, 독립 감사로 커버리지 gap 탐색. **직접 판단한 것** — 문제 선정(예방이 아닌 '발생 후 대응'), 14종 시나리오를 법 조문 단위로 확정하는 커버리지 프레임, 스킬 경계(무엇을 넣고 뺄지).

**막혔던 지점·해결** — ① 스킬 트리거 자동평가가 이 환경에서 신뢰 불가 → 서브에이전트 라우팅 테스트(22/22)로 대체. ② 이용자수 미상을 '0명'으로 표기해 오판정 위험 → `null`=미상 + 재판정 경고로 수정. ③ 정합성 검증기 자체 버그(정규식이 값셀 대신 키셀·반환타입 오해)를 검증기가 되레 드러냄 → 수정.

**받아들이지 않은 AI 제안** — (a) 보상 산정 스킬: 사내 OMS·예외가 많아 conversational에 부적합해 제외. (b) 스킬명 번호 프리픽스: 흐름이 조건부·병렬이라 1→2→3이 오해를 유발해 거부하고, 대신 진입점 오케스트레이터 스킬을 채택.

### 5. 어떻게 검증했나요? *(800자 이내)*
**입력→결과 예시** — 2025.10.8 DriveWealth 연계 장애를 `incident.json`으로 입력(외부요인·중단 17분·규모 미상) → 금감원 보고 **'비대상'**(17분<30분, 규모 미상이라 '1만명 재판정 필요' 경고) + 고객 실시간공지 + 병행신고 없음(개인정보 무관) + 이사회 비대상. 반대로 블루오션 ATS 사태(중단 지속·외부 제3자+타사 동시영향)는 이사회 **'대상'**(가중요인 2개)으로 갈린다.

**정상·예외 확인** — 현행 법령상 구분되는 14종 시나리오 판정을 기대값과 대조해 **14/14 일치**, 실제 공개 장애 8건을 재현해 대상 5·비대상 3·이사회 블루오션 1건을 확인했다. 예외는 필드 누락·enum 위반·미상(null)·복구 전·브라우저 부재를 각각 넣어 크래시·오판정이 없는지 봤고(**pytest 25건**), 일부러 깨뜨린 enum이 실제로 차단되는지까지(음성 테스트) 확인했다.

**의심한 것·아직 부족한 것** — 개별 사건의 이용자수·금액이 언론 비공개라 대부분 미상이며, 정확 판정엔 실제 내부 로그가 필요하다. 정보통신망법의 증권사 포섭은 법적 판단이 필요해 '경고 플래그'까지만 뒀다. **테스트하며 고친 점** — 이용자수 0명→미상, 병행신고 한 줄 뭉침→불릿, 경영진 보고 제목 하드코딩 '전산장애'→실제 사고유형 반영.

> **근거·출처 원칙**: 정량 수치는 국회 정무위 제출자료·언론보도 등 **공개 자료**(위 참고 URL) 기반이며, 규정 판정은 **법제처 현행 조문**에 근거함. 기업 내부 비공개 정보·확인 불가 수치는 쓰지 않았고, 미확인 항목은 `미상`으로 명시함. 사건별 세부 출처는 [`../장애사례_아카이브/README_장애사례_리스트.md`](evidence/장애사례_아카이브/README_장애사례_리스트.md), 법령 현행성 감사는 [`../03_커버리지테스트_결과.md`](evidence/03_커버리지테스트_결과.md) §4 참조.

## 구성 — 1개 플러그인 = 진입점 1 + 대응 스킬 5 + 공통 유틸

모든 스킬은 공통 데이터 모델 [`shared/incident.schema.json`](src/shared/incident.schema.json)(`incident.json`)을 공유함. 한 번 입력한 사실이 모든 산출물에 일관되게 흐름. 산출물은 항상 `.md`(+PDF)로 `<incident 폴더>/out/`에 자동 저장됨.

| 스킬 | 디렉터리 | 산출물 | 근거 |
|---|---|---|---|
| **진입점** 사고 대응 시작 | `skills/incident-response` | 트리아지 + 조건부 대응 순서 안내 + 하위 스킬 호출 | 오케스트레이터 |
| 1. 금감원 사고보고서 | `skills/regulator-incident-report` | 별지 제2호서식 초안(최초/중간/종결) + EFARS 필드블록 + **공식 PDF**(표지+별첨1) | 전자금융감독규정 시행세칙 제7조의4 |
| 2. 고객 공지문 | `skills/customer-outage-notice` | 실시간/복구, 3채널(홈피·MTS·알림톡) | 약관·소비자보호 |
| 3. 경영진·이사회 보고서 | `skills/exec-board-report` | 경영진 속보 / 이사회 보고서 + 보고대상 자동판정 + 병행신고 | 전자금융감독규정(2025.8.5)·지배구조법 |
| 4. 개인정보 유출 신고 | `skills/privacy-breach-filing` | 정보주체 통지문 + 감독기관 신고서 + 72h 시한 + 신용정보법 이원신고 | 개인정보보호법 §34·시행령 §40, 신용정보법 §39조의4 |
| 5. 대응 시한 대시보드 | `skills/response-deadline-tracker` | 규제 시한 D-counter(금감원 24h·KISA 24h·유출 72h·보상 14영업일) | 보고 단계별 deadline |

> **보상 산정은 스킬에서 제외함**. 보상액 계산은 수천 건 주문·체결 데이터 배치 연산으로 **사내 OMS/정산 시스템**의 몫이며 예외 케이스가 많아 conversational 스킬에 부적합하기 때문. 단 보상 통지 **기한**(접수+14영업일)은 response-deadline-tracker가, 보상 **안내 문구**는 customer-outage-notice가 담당함.

### 공통 유틸 (`shared/scripts/`)
- `run_all_skills.py` — 한 사건에 전 스킬 일괄 실행(사전검증 → 6스킬 → 정합성 검증).
- `form_mapping.py` — 별지 서식 체크박스 매핑의 **단일 원천**(md·PDF·검증기 공용).
- `validate_incident.py` — 실행 전 스키마 enum·필수필드 사전 검증(각 스킬 내장).
- `verify_fss_consistency.py` — incident.json ↔ md ↔ PDF 3자 정합성 가드레일.
- `set_status.py` — 산출물 생성/제출 후 `reporting{}` 상태 write-back(대시보드 정확도).
