# 고객 장애 공지문 생성기

장애 발생 시 고객에게 나갈 공지문을 만든다. 카카오페이증권의 과거 실패(2025.10: '정상화' 공지 후에도 미복구, 원인 누락, 이전 공지 재사용)를 막도록 설계됐다.

## 경계
- **문안 생성까지만.** 실제 게시·알림톡 발송은 하지 않는다(별도 채널 시스템).
- 숫자·사실을 **지어내지 않는다.** 미입력은 비워두고 보완 요청.

## 입력
- `incident.json` (`shared/incident.schema.json` 구조) + 회사 상수 `shared/company.json`(고객센터 번호·보상안내 URL·필수항목·14영업일 등).
- incident.json이 없으면 자유서술로 묻지 말고 **AskUserQuestion 도구로 필요한 사실을 한 필드씩 구조화해 묻는다**(regulator-incident-report와 동일한 인테이크 방식). 시각 등 정확값이 필요한 항목만 짧게 텍스트로 받는다.
- **⛔ 철칙 — 추측 금지**: 발생시각·영향 서비스·복구 여부·원인 등을 **임의로 지어내지 않는다.** 모르면 '파악 중/미상'으로 두고 보완 요청한다. 특히 **복구 여부는 추측 금지** — `timeline.resolved_at`이 확정되지 않으면 realtime 공지만 내보내고, recovery('정상화') 공지는 스크립트가 자동 거부한다(exit 2).
- **개인정보 유출 동반 시**: 고객 대상 **정보주체 통지문은 이 스킬이 아니라 `privacy-breach-filing`가 생성**한다(개인정보보호법 제34조 5대 포함사항). 이 스킬의 장애 공지와 혼동하지 말 것.
- **자동 사전 검증**: 스크립트 실행 시 enum·필수필드를 자동 점검하고 오류 시 중단(`--no-validate`로 우회). `run_all_skills.py`도 맨 앞에서 1회 검증.

## 실행 절차
1. **모드 결정**: `realtime`(진행 중) / `recovery`(복구 완료). 미지정 시 `auto`(resolved_at 있으면 recovery).
2. **스크립트 실행**:
   ```bash
   python3 scripts/generate_customer_notice.py <incident.json> --mode <realtime|recovery|auto>
   ```
   - **산출물은 항상 `.md` 파일로 자동 저장**된다: `<incident 폴더>/out/<id>_고객공지_<모드>.md`. 저장 경로는 `--out`으로 변경, 저장 생략은 `--stdout-only`. 저장된 파일 경로를 사용자에게 반드시 알린다.
3. **가드 확인**:
   - **복구 공지 잠금**: `timeline.resolved_at`이 없으면 recovery는 거부된다(exit 2). 실제 복구 확인 후 `resolved_at`을 채워 재실행하라고 안내. 그 전엔 realtime만 게시.
   - **원인 포함 강제**: recovery인데 `cause.root_cause`가 비었거나 '파악 중'이면 경고가 뜬다. 원인을 확정해 넣은 뒤 게시.
4. **문구 윤문 (모델 역할)**: 스크립트는 골격을 만든다. 다음을 다듬어라(사실 추가 금지):
   - 영향 서비스가 길게 나열되면 자연스럽게 압축(예: "해외주식 매수/매도 주문, 해외주식 체결" → "해외주식 거래").
   - 복구 공지의 '원인'을 고객이 이해할 1문장으로 정리(예: 외부 브로커 장애 → "해외주식 체결을 담당하는 외부 시스템의 일시 장애").
   - 알림톡이 권장 글자수(`company.json`의 `alimtalk_char_target`)를 넘으면 핵심만 남겨 줄인다.
5. **전달**: 3개 채널 문안을 모드와 함께 사용자에게 전달. recovery면 보상 신청 안내(고객센터·필요정보·14영업일)가 포함됐는지 확인.

## 채널별 성격
- **홈페이지/MTS 상세**: 발생시각·영향범위·(realtime)대체 주문수단·(recovery)원인·보상절차.
- **알림톡 압축**: 핵심 1~2문장 + 연락처/링크. 글자수 주의.
- **요약 배너**: 한 줄 상태 표시.

## 데이터 모델 변경
공지에 필요한 새 사실(예: 예상 복구시각 필드)이 생기면 `shared/incident.schema.json`과 스크립트를 함께 갱신하고 사용자에게 알린다.
