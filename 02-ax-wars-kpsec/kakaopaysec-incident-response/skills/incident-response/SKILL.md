# 전자금융사고 대응 — 시작(오케스트레이터)

장애·사고 발생 시 **여기서 시작한다.** 사고를 분류하고, 규제 시한에 맞는 **대응 순서**를 안내하며, 필요한 하위 스킬을 호출한다. 이 플러그인의 산출물은 모두 **초안 생성까지만** 하고 실제 제출·발송은 담당자가 한다.

## 경계
- **안내·오케스트레이션까지만.** 판정·산출물은 하위 스킬이, 실제 제출·발송·심의는 사람이 한다.
- 숫자·사실을 **지어내지 않는다.** 모르면 '파악 중/미상'으로 두고 확인한다(추측 금지).

## 실행 절차

### 1) 사고 트리아지 (AskUserQuestion, 라우팅에 필요한 최소)
자유서술로 묻지 말고 **AskUserQuestion으로 한 문항씩** 받는다. 이 답으로 어떤 스킬이 필요한지 갈린다.
1. **사고 유형** (header `사고유형`) — 전산장애(서비스 지연·중단) / 침해사고(해킹·악성코드·DDoS·정보유출) / 전자금융사기(피싱·명의도용) / 파악 중
2. **복구 여부** (header `복구여부`) — 진행 중 / 복구 완료
3. **개인정보·신용정보 유출 동반** (header `개인정보`) — 없음 / 개인정보 / 신용정보 포함 / 둘 다 / 파악 중
4. **영향 규모·중단시간** (header `규모`) — 정확값 직접 입력 권장 / 대략(구간) / 미상  *(임계 30분·1만명 부근이면 정확값 확인)*

### 2) incident.json 생성·확인 (단일 사실 원장)
- 공통 데이터 모델 `shared/incident.schema.json` 구조의 `incident.json`을 만든다(이미 있으면 재사용).
- 트리아지 답 + 시각(인지/발생/복구)·시스템명·사고내용을 매핑한다. 한 번 입력한 사실이 모든 산출물에 일관되게 흐른다.
- 실행 전 `python3 shared/scripts/validate_incident.py <incident.json>`로 enum·필수필드를 검증(각 스킬도 자동 검증).

### 3) 대응 순서 안내 (조건부·병렬 — 번호가 아니라 시한 기준)
사고유형·복구여부·개인정보 동반에 따라 아래 순서로 안내·실행한다. **모든 사고가 전부를 거치지 않는다.**

| 시점 | 무엇 | 스킬 | 조건 |
|---|---|---|---|
| **즉시(최우선)** | 고객 실시간 공지 | `customer-outage-notice` (realtime) | 진행 중이면 즉시 |
| **인지+24h 내** | 금감원 사고보고(별지 제2호서식) | `regulator-incident-report` | 보고대상 판정 후. 전 사고 |
| **병행(갈음 안 됨)** | 침해사고 KISA 신고(24h) / 개인정보 유출 신고(72h) | `privacy-breach-filing` | 침해사고 또는 PII 동반 시 |
| **중대 시** | 경영진 속보·이사회 보고 | `exec-board-report` | 침해·개인정보 또는 가중요인 2개↑ |
| **복구 후** | 고객 복구공지 / 금감원 종결보고 / 보상통지 | `customer-outage-notice`(recovery)·`regulator-incident-report`(final) | `resolved_at` 확정 후 |
| **상시** | 남은 시한·진행상황 대시보드 | `response-deadline-tracker` | 언제든 "지금 가장 급한 것" 확인 |

- **핵심 순서 원칙**: 고객 실시간 공지는 **가장 먼저(즉시)**, 규제 보고는 **시한(24h/72h)** 안에, 복구 공지·종결·보상은 **복구 확인 후**. `resolved_at`이 없으면 복구/종결 산출물은 잠긴다.

### 4) 실행 방식 (택1)
- **단계별**: 위 표 순서로 사용자에게 다음 할 일을 짚어주고, 해당 하위 스킬을 차례로 호출한다.
- **일괄 생성**: 초기 대응 산출물을 한 번에 만들려면
  ```bash
  python3 shared/scripts/run_all_skills.py <incident.json>
  ```
  (금감원 보고·PDF·고객공지·경영진/이사회·유출판정·타임라인을 생성하고 사전검증·정합성 검증까지 자동 수행)
- 이후 상황이 바뀔 때마다 `response-deadline-tracker`로 진행상황을 갱신·추적한다.

## 모델 역할
- 트리아지 결과와 **권장 순서를 사용자에게 먼저 요약**한 뒤 진행한다(왜 지금 이 순서인지).
- 사고유형·개인정보·규모가 미상이면 **추측하지 말고 반드시 확인**한다.
- 각 산출물 생성 후 `reporting{}` 상태를 갱신(`shared/scripts/set_status.py`)해 대시보드 정확도를 유지한다.
