# gaap-ifrs & gaap-standards-qa — GAAP↔K-IFRS 스위트 (AX 인재전쟁 · 대상: 삼일PwC)

한 플러그인, 두 트랙. **트랙 1**은 소스 회계기준 시산표를 넣으면 K-IFRS 재무제표 + 전환조정 명세서(기준서 인용) + 영향분석을 산출하는 근거기반 변환 엔진(지원 소스 GAAP: 일반기업회계기준(K-GAAP)·베트남(VAS)·중국(CAS)·미국(US GAAP)). **트랙 2**는 3개 소스 GAAP 원문(K-IFRS 63기준서·일반기업회계기준 36장·중국 CAS 95문서, 합 **9,903문단**)을 하이브리드(BM25+벡터, 교차언어) 검색해 원문 인용 없이는 답하지 않는 로컬 MCP grounded 챗봇이다. 두 트랙 모두 "회계기준 전환·조회를 위해 로컬 GAAP과 IFRS를 둘 다 아는 희소 시니어에 의존하는" 같은 병목을, 트랙 1은 자동조정(확정 답), 트랙 2는 원문검색(열린 질의)으로 다른 각도에서 푼다.

**실행(트랙 1):** `cd gaap-ifrs && pip install -e .` 후 `gaap-ifrs convert --input tb.xlsx --extra adjustments.json --out out/`
**실행(트랙 2):** `pip install -e .` 후 `.mcp.json`으로 등록된 `gaap-standards` MCP를 Codex/Claude Code가 호출(스킬 `gaap-standards-qa`가 회계기준 질의 시 자동 트리거).

---

## 1. 무엇을, 누가, 어떤 상황에서 쓰나요?

#### 트랙 1 — GAAP → K-IFRS 변환 엔진

삼일PwC Assurance LOS의 **회계기준 전환 자문** 실무자(주니어~매니저)가 씁니다. 두 상황이 핵심입니다. ① 비상장사가 **IPO 상장전환**을 위해 일반기업회계기준을 K-IFRS로 바꿔야 할 때, ② 국내 대기업이 **해외 자회사(베트남·중국 등)의 로컬 GAAP을 모회사 K-IFRS로 연결**해야 할 때. 회사가 준 시산표를 받아 계정을 IFRS 체계로 재분류하고, 대손(ECL)·리스·유형자산 재평가·개발비 같은 측정차이를 조정하는 일은, 지금은 "로컬 GAAP과 IFRS를 둘 다 깊게 아는 희소 시니어"가 병목입니다. 이 엔진으로 주니어가 CLI 한 줄이면 **초안 + 각 조정의 기준서 근거 + 손익·자본 영향**을 받아, 검토·판단이라는 고부가 업무에 집중하게 됩니다(전문성 민주화 → 인재전쟁 대응).

#### 트랙 2 — 회계기준 원문 grounded RAG 챗봇

같은 실무자가, 트랙 1의 6개 자동조정에 없는 조항을 찾거나 "이 계정 관련 조항이 원문에 정확히 뭐라고 돼 있지?"를 확인할 때 씁니다. 지금은 기준서 PDF·HWP 수십~수백 페이지를 직접 뒤지거나, 일반 생성형 AI에 물어 그럴듯하지만 틀린 조항번호·문언(할루시네이션)을 받는 위험이 있습니다. 로컬 MCP `gaap-standards`가 K-IFRS·일반기업회계기준·중국 CAS 원문 **9,903개 문단**을 BM25+벡터 하이브리드(교차언어)로 검색해 **검색된 문단의 원문(verbatim)만 인용**하고, 근거가 없으면 "근거 없음"이라 답합니다 — 감사·자문 산출물에 잘못된 조항 인용이 들어가는 리스크를 원천 차단합니다.

## 2. 왜 이 문제를 선택했나요?

삼일PwC Assurance의 구조적 문제는 **감사 커모디티화**입니다. 평균 감사보수가 −4.5% 하락하는데 인건비는 매출(+15%)보다 빠르게(+18%) 늘어, 영업이익률이 제52기 4.29%→제54기 1.60%로 붕괴했습니다(DART 1차). 해법은 저마진 감사의 비용절감이 아니라, **Assurance 내 고마진 자문(비감사 용역) 비중을 높이고 이를 AI로 저비용 수행**하는 것입니다.

#### 트랙 1 — 왜 GAAP→IFRS 전환 자문인가

그중 **GAAP→IFRS 전환 자문**을 고른 이유: (1) 삼일이 "재무제표 작성·회계기준 전환 지원"으로 **실제 서비스**하고, (2) 양쪽 기준을 아는 **희소 전문가가 병목**이라 AI 레버리지가 크며, (3) 빅4 비교가이드·K-IFRS가 **공개**돼 할루시네이션 없는 근거화가 가능합니다. 특히 2022년부터 해외 자회사 포함 **연결 의무화**로, 국내 대기업 자회사 밀집 1위 중국(CAS)·3위 베트남(VAS) 전환 수요가 큽니다(자체 DART 분석).

#### 트랙 2 — 왜 grounded 원문 검색인가

같은 근본원인(감사 커모디티화)에서 출발하되 다른 실패모드를 겨냥합니다: 자문 산출물에 **잘못된 조항 인용**이 섞이면 신뢰·재작업 리스크가 큽니다. 일반 LLM은 조항번호·문언을 그럴듯하게 지어내는 경향이 있어, "원문 그대로"가 생명인 회계기준 도메인에는 grounded 검색이 필수라고 판단했습니다. 트랙 1의 변환 엔진도 `basis`(조항 근거) 필드를 인용하는데, 트랙 2는 그 근거를 직접 검증·확장하는 인프라 역할도 겸합니다(트랙 1이 다루지 못하는 조항은 트랙 2로 원문을 직접 확인).

## 3. 플러그인은 어떻게 작동하나요?

#### 트랙 1 — 변환 파이프라인

파이프라인: `parse(시산표→canonical) → map(Layer1 재분류) → adjust(Layer2 측정조정) → build(IFRS BS/PL) → reconcile(전환 브릿지) → impact(영향) → report(Excel/JSON)`.

- **지식 = 근거, 계산 = 코드 (분리).** 계정→IFRS 매핑과 조정 규칙은 `data/*.json`에 **기준서 인용과 함께** 저장(구조적 큐레이션 RAG, 벡터DB 없음). 숫자는 결정론적 파이썬이 계산 → 재현·검증 가능.
- **Layer 1(재분류):** 시산표만으로 전 계정 IFRS 표시체계로 매핑(K-GAAP 49·US GAAP 26·CAS 17·VAS 14 계정, 주요 10계정은 조항 근거 포함).
- **Layer 2(측정조정): 6개** — ECL(1109)·리스(1116, 감가상각+이자 P&L 패턴)·재평가(1016)·개발비(1038)·확정급여(1019)·금융상품 공정가치(1109 FVPL/FVOCI). 각 조정은 **복식부기 entries**로 자산·부채·자본을 정확히 이동.
- **정보 부족/판단 필요 시:** 매핑 없는 계정, 조정에 필요한 보조자료(연령표·리스스케줄 등)가 없으면 **숫자를 지어내지 않고 flagged("판단/추가자료 필요")** 로 표기. 커버리지는 넓게 진단하되 자동계산은 데이터 허용만큼만.
- **corpus-pluggable:** 소스 GAAP은 코퍼스+규칙 플러그(`load_mappings(source_gaap)`). 국내(K-GAAP)로 증명 → VAS·CAS·US GAAP로 확장.

세부는 `gaap-ifrs/README.md` 참조.

#### 트랙 2 — grounded 검색 파이프라인

빌드타임(`tools/ingest/`): 기준서 원문(PDF/HWP/HTML) 다운로드 → 형식별 추출 → 문단정렬 청킹 → **충실도 게이트**(원문 대비 라운드트립 커버리지 ≥99.5%, 모지바케 검출)를 통과한 문단만 → 임베딩(`intfloat/multilingual-e5-small`) + faiss PQ 인덱스로 `corpus/`에 패킹.

런타임(`gaap_standards_mcp`): stdio MCP 서버가 `search_standards`(BM25+벡터를 RRF로 융합한 하이브리드 검색)·`get_paragraph`·`get_context`·`list_standards` 4개 도구를 제공. 스킬 `gaap-standards-qa`가 먼저 검색하고, 반환된 문단의 `text`(원문 verbatim)만 근거로 `[출처: {gaap} 제{no}호 문단 {no} · {url}]` 형식으로 인용한다.

**정보 부족/판단 필요 시:** 검색 결과가 없거나 무관하면 "근거를 찾지 못했습니다(근거 없음)"라 답하고 추측하지 않는다. 임베딩 모델·벡터 인덱스가 없으면 BM25 단독(**degraded**, 교차언어 리콜 저하를 고지), MCP 서버 자체가 불가하면 내장 경량 BM25 진입 스크립트(**no-mcp**)로 이어지는 3단 폴백이며, 어느 경로로 답했는지 항상 고지한다.

세부는 `README_track2.md`, `skills/gaap-standards-qa/SKILL.md` 참조.

## 4. AI를 어떻게 썼나요?

**최종 숫자는 AI가 만들지 않습니다.**

#### 트랙 1

파이프라인 런타임에는 LLM이 돌지 않고, 결정론적 코드 + 인용 JSON으로만 동작합니다. AI(LLM)는 코드가 못 하는 **퍼지 앞단**에만 쓰는 설계입니다: 지저분한 엑셀 파싱, 계정명 의미 매칭(정확/alias 실패 시), 계약서에서 리스 조건 추출. 그 산출물도 결정론 계산에 투입되고 근거 없으면 flag됩니다.

**직접 판단한 것:** ① 조정을 "equity_effect 단일 숫자"가 아니라 **복식부기 entries**로 모델링(자산=부채+자본 균형이 코드로 강제되게) — AI가 처음 제안한 단일 amount 방식을 **거부**했습니다. 균형이 안 맞고 리스·재평가처럼 자본을 안 거치는 조정을 못 담기 때문입니다. ② ECL·리스의 **부호 규약**(환입 +, 전진배분 −)을 직접 검산해 테스트로 고정. ③ RAG를 벡터DB(Chroma/Milvus)로 하자는 방향을 **거부**하고, 인용 정확성이 생명인 회계 특성상 구조적 큐레이션 검색으로 결정.

#### 트랙 2

AI에게 맡긴 일: PDF/HWP 등 형식별 추출기 초안, 문단 경계 정규식 설계 초안, faiss 인덱싱 보일러플레이트. **직접 판단한 것:** ① 트랙 1은 계정 매핑(60개 남짓 고정 규칙)이라 벡터DB를 **거부**했지만, 트랙 2는 9,903개 자유텍스트 문단(3개 GAAP)이라 큐레이션이 안 통하므로 반대로 **하이브리드(BM25+벡터)를 채택** — 코퍼스 성격에 따라 반대 결론을 낸 것 자체가 의도적 판단입니다. ② 검색·임베딩용 정규화 텍스트(`text_norm`)와 인용용 원문(`text`)을 **분리 저장** — AI가 처음엔 정규화 텍스트 하나만 저장하자고 제안했지만, 인용이 원문과 한 글자라도 다르면 안 되는 도메인이라 **거부**하고 이중 저장으로 바꿨습니다. ③ BM25 점수와 코사인 유사도는 스케일이 달라 단순 가중합은 부정확 — AI가 제안한 점수 정규화 합산 대신 **RRF(순위 기반 융합)**로 결정했습니다.

## 5. 어떻게 검증했나요?

#### 트랙 1

**입력→출력 예시(완성 예제 `examples/kgaap/`):** K-GAAP 시산표(단위 KRW) + 보조자료를 넣으면 → **6개 측정조정을 전부 계산**해 자본총계 **50,000,000 → 56,341,074**(Δ +6,341,074)를 산출. 각 조정의 자본영향: 확정급여 −1,000,000·개발비 −1,200,000·ECL +160,000·금융상품 +700,000·리스 −318,926·재평가 +8,000,000. 예: ECL은 `목표충당금 = Σ(채권×손실률)`을 계산해 환입/추가충당을 잡고, 리스는 PV 할인 + 감가상각·이자로 순이익 전진배분을 반영한다. 산출된 `difference_analysis.md`에는 계정·조정마다 **조항 근거·판단 논리·분개 파급효과(자산·부채·자본·순이익)** 가 단위와 함께 기록된다.

**정상/예외:** 보조자료가 있으면 계산, 없으면 **flagged**("판단 필요") — 예외경로를 CLI로 확인. `pytest` **34 케이스**로 파싱·매핑·조정 6종·명세·영향·CLI·VAS·CAS·US GAAP·검증기를 고정.

**IFRS 1101 검증기:** 엔진 산출 IFRS 자본·조정을 전환상장사 첫 K-IFRS 주석의 **전환조정 정답셋과 대조**(일치/불일치). 4개 조정 전환 픽스처로 데모 PASS(`analysis/validate_transition_demo.py`, 자본 15,305,000 일치).

**아직 부족한 점:** 수익인식(1115)·자산손상(1036) 등 잔여 조정 확장 필요, 대형사 전환주석 자동추출은 2011년 전후 공시 문서형식(HWP/PDF 첨부) 편차로 best-effort. 조항 원문은 현재 큐레이션(발췌·인용)으로, 정식 제출 시 공식 원문과 대조가 필요합니다.

#### 트랙 2

**입력→출력 예시:** `search_standards("리스 사용권자산 인식")` 호출 → 1순위로 **K-IFRS 1116호 문단 22 "리스이용자는 리스개시일에 사용권자산과 리스부채를 인식한다."** 를 원문 그대로 반환(하이브리드 full 모드, 실측 확인). 같은 코퍼스에서 BM25 단독 경로(`fallback.fallback_search`)로도 동일 문단이 1순위로 나옴을 재확인.

**적재 현황:** 3개 소스 GAAP **9,903문단** — K-IFRS(63기준서·6,137) + 일반기업회계기준(36장·2,101) + 중국 CAS(95문서·1,665)(`corpus/manifest.json`). 전수 스캔 결과 **leak 0·id충돌 0**, 모지바케(치환문자) 0건. 벡터는 다국어 임베딩(`multilingual-e5-small`)이라 **교차언어 검색**(중국어 질의 '租赁 使用权资产'→CAS 제21호 실측). `pytest` **97 케이스**로 BM25·벡터·RRF융합·하이브리드 검색·GAAP별 세그멘터·leak/shadow 게이트·corpus 스키마·MCP 4도구·3단 폴백(full/degraded/no-mcp)·패킹·manifest·SKILL.md 계약을 고정.

**정상/예외:** 벡터 인덱스 없음(degraded)·MCP 불가(no-mcp) 경로는 합성 fixture로 pytest가 확인.

**아직 부족한 점:** 원문 코퍼스는 **K-IFRS·일반기업회계기준·중국 CAS 3개** 적재 완료 — **베트남 VAS는 보류**(공식 베트남어 원문 vs 펌 영문 번역본 중 출처 결정 필요; 번역본을 원문으로 싣지 않기 위함), **US GAAP는 원격 확장 지점**(asc.fasb.org 봇월 차단으로 zip 내장 불가, 별도 라이선스 원문 확보 필요)으로 남겨둔다. 임베딩 모델은 zip에 넣지 않아 최초 실행 시 다운로드하며, 실패하면 자동으로 BM25 단독(degraded)으로 동작한다(정확도 저하는 항상 고지). 두 트랙의 산출물은 모두 **전문가 검토용 초안**이며 감사의견·법적 효력을 갖지 않습니다.
