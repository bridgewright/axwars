# 02. 감사 실무 워크플로 & 자동화 공백 분석 (실무자 1차 리서치)

> 목적: Codex 플러그인이 겨냥할 **"아직 자동화 안 된 잔여 수작업"** 을 특정한다.
> 렌즈: 타깃 = **반복적 ∩ 기존 자동화(매크로·펌툴·AI)가 못 건드린 것 ∩ 에이전트 능력이 필요한 모양 ∩ 예선 크기**. "가장 큰 병목"이 아니라 **자동화 잔여물(residual)** 을 찾는다.
> 방법: 감사 실무자 네이버 블로그 1차 마이닝 + 공개 표준/데이터 교차. 익명 블로그는 [confidence: medium], 수렴 시 상향.

---

## 1. 감사 주니어의 실제 워크플로 (실무자 기록 기반)

기말감사(12월결산 → 1~3월 시즌) 주니어 업무 흐름은 실무자 기록에서 다음으로 수렴한다 (better_today1721, brightsso97):

```
① PBC(자료요청) → ② 회신 대기/독촉 → ③ Key-in(종이·PDF→엑셀 수기입력)
→ ④ Refer check/tie-out(증빙↔FS↔조서↔주석 대사) → ⑤ 연결정산·계정 재분류
→ ⑥ 조서 작성·닦기 → ⑦ 풋팅(footing, 최종 숫자 정합성) → ⑧ 리뷰
```

- **② 회신 대기 병목 확인:** "조회서는 보내는 것보다 받는 게 더 힘들다... 회신 늦어지면 매일 전화 돌리기" (better_today1721 1편). 사용자가 지목한 "메일 요청→회신 대기" 병목이 실재.
- **③~⑤ 수작업 확인:** "종이 출력물을 사람 손으로 하나하나 엑셀로 옮긴다... 숫자 하나 틀리면 합계가 틀어진다" (3편).
- **강도:** 2월 새벽 2시 퇴근 기본, 3월 해뜰 때 퇴근 (1편) — §01 문서의 "주 100시간" 정성 뒷받침.

## 2. 이미 자동화된 것 (SUBTRACT — 스코프 아웃)

"큰 문제는 이미 나름 풀어놨다"는 가설이 실무자 기록으로 확인된다. 아래는 **빼야 할** 영역이다.

| 과거 수작업 | 현재 해결 수단 | 출처 |
|---|---|---|
| 금융기관 조회서 발송·회수·우편환 | **전자조회 시스템**(버튼 클릭·화면 조회) | better_today1721 1편 |
| 원장·분개장 raw export 정리 | 개인 **파이썬/매크로** (포맷이 시스템별로 고정) | jcw6014 |
| 표준재무제표 작성(CoA→표준코드) | **매크로**(단, 매년 같은 회사만) | jcw6014 |
| 정형 조서 생성·재계산(감가상각·리스부채) | **Claude for Excel**("33개 시트 5분") | fancy303 |
| 세무 질의응답 | **삼일 Tax Agent**("강력하나 결론 피상적") | jcw6014 |
| 예규·판례 모니터링 | 개인 **알림봇** | jcw6014 |

→ **핵심 발견 1: 매크로·기존툴은 "포맷이 고정된 반복"만 푼다.** CoA 매핑 매크로는 "매년 같은 회사"에서만 동작하고, 원장 정리 파이썬은 "뽑히는 형식이 늘 같으니까" 가능했다. **포맷·구조가 매번 달라지는 순간 정적 자동화는 깨진다.** 여기가 잔여물의 위치다.

## 3. 잔여 공백 (agent-shaped residual)

매크로가 구조적으로 못 하고, 2026년 현재도 손으로 하는 것:

### 후보 A — 이종(異種) 소스 계정 매핑 / 연결 재분류
- **실무:** 자회사 N개가 각각 더존·SAP·자체ERP → "계정과목 이름도, 출력양식도, 분류기준도 다 다르다 → 모회사 기준으로 재가공" (better_today1721 3편). 안 맞으면 "3천만원이 어디서 틀어졌나" 추적.
- **왜 매크로가 못 푸나:** 엔게이지먼트/자회사마다 스키마가 달라 정적 매핑이 깨짐. **퍼지 의미 매핑**(적요·계정명이 다를 때 뜻으로 연결)이 필요.
- **왜 에이전트/Codex 감:** 매번 다른 시산표를 읽고 **대사 로직을 그때그때 코드로 생성**해 흡수. jcw6014의 "매년 같은 회사만 되는 CoA 매크로"의 한계를 정확히 메움.
- **크기·데모:** 다소 큼. 공개 데이터 데모는 가공 필요.

### 후보 B — 문서 교차 tie-out (삼각대사: 정산표↔재무제표 본문↔주석)
- **실무:** "삼각 대사: 정산표 ↔ 재무제표 본문 ↔ 주석 상세가 일치하는가... 수평/수직 합계... 전기 이월... 주석 참조... 현금흐름표-주석 대사" — **2026년 현재도 출력본에 빨간펜 수기** (audit2finance 풋팅 체크리스트).
- **왜 매크로가 못 푸나:** 조서(엑셀) + 재무제표 본문 + 주석(문서/PDF)에 걸쳐 있어 스프레드시트 내부 함수로 안 닫힘. Claude for Excel도 **엑셀 밖(주석 문서)까지는 못 건넘**.
- **왜 에이전트/Codex 감:** 여러 포맷 문서를 읽어 숫자를 뽑고, 정합성 규칙(체크리스트가 곧 스펙)을 코드로 검증. **풋팅 체크리스트 자체가 이미 완성된 요구사항 명세**다.
- **크기·데모:** **예선급 + 공개 DART 사업보고서(재무제표+주석 XBRL)로 즉시 시연 가능.** ← 가장 유력.

### 후보 C — 증빙 대사(vouching): 원장 항목 ↔ 계약서/증빙 PDF
- **실무:** 사용자 예시. 비정형 문서 읽기 + 퍼지 매칭.
- **한계:** 실제 증빙이 클라이언트 기밀 → 공개 데모가 어려움(가상 데이터 필요).

## 4. 문제를 다시 규정한 두 개의 결정적 제약 (신규 발견)

### 제약 1 — 보안·비밀엄수 → "로컬 에이전트" 형태가 유리
- "보안 때문에 **클라이언트 자료를 외부 AI에 넣을 수 없고**, 회사가 정해준 도구 안에서만" (jcw6014). 법적 근거: **공인회계사법 §20, 외감법 §20, 개인정보보호법 §18(비밀엄수)**.
- **함의:** SaaS 업로드형은 채택 장벽이 크다. **로컬에서 도는 코드 에이전트(Codex/Claude Code)** 는 이 제약에 오히려 정합 — 데이터가 로컬을 안 벗어난다. 이게 Codex 플러그인 form-factor의 **구조적 우위**.

### 제약 2 — 정적 자동화의 한계는 "포맷 변동"
- §2의 결론: 매크로가 푸는 건 고정포맷 반복. 잔여물은 **매번 데이터가 달라 정적 스크립트가 깨지는 곳**. Codex는 "매번 새 코드 생성"으로 이 변동을 흡수한다 → 대체가 아니라 **매크로가 못 버틴 틈만** 겨냥.

## 5. 경쟁·성숙도 신호 (중복 회피용)

- **procpalee "회계실무 AX 프로젝트":** 한 현직 회계사가 **Claude Code를 오케스트레이터로** 감사조서·내부회계·결산·평가 에이전트 + 기준서 RAG MCP + OpenDART MCP + 템플릿/스킬 + engagement(PBC) 관리를 쌓는 중. → **(a) form-factor·수요 검증(코드 에이전트가 맞다), (b) 경고: 전체 오케스트레이터를 통째로 만드는 건 예선 범위 밖 — 날카로운 한 조각만 잡아야.**
- **Claude for Excel:** 엑셀 내부 조서 생성은 이미 콜로나이즈드 → 우리는 **엑셀 밖(문서 교차)** 으로 가야 차별화.
- **삼일 Tax Agent:** 세무 Q&A는 삼일이 선점 + "피상적" 천장 → 세무 근거검색은 후순위.

## 6. 좁혀진 결론 (다음 단계 입력)

- **1순위: 후보 B(문서 교차 tie-out / 풋팅 자동검증).** 이유: ① 2026년 현재도 수기, ② 체크리스트=완성된 스펙, ③ 공개 DART로 데모 완결, ④ Claude for Excel·매크로가 못 넘는 "문서 밖 교차", ⑤ 로컬 실행으로 보안 제약 회피, ⑥ 예선 크기.
- **2순위: 후보 A(이종 계정 매핑).** 임팩트 크나 사이즈·데모 부담.
- **후보 C·세무:** 데모/경쟁 이유로 후순위.
- **form-factor:** 로컬 코드 에이전트(Codex/Claude Code)가 보안·포맷변동 두 제약에 정합 → 플러그인 형태 타당성 확보.

→ 다음: 후보 B를 스펙으로 확정(입력·출력·검증 시나리오·DART 데모 데이터)해 `03_solution-scope`로.
