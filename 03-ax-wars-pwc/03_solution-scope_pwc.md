## 0. 한 줄 정의 · 대상 사용자

**소스 GAAP 시산표를 넣으면 → IFRS 재무제표 + 전환조정 명세서(근거인용) + 영향분석을 산출하는, 근거기반 회계기준 변환 엔진.**

- **사용자:** 삼일PwC Assurance LOS의 **회계기준 전환 자문** 실무자(주니어~매니저). 병목 = "로컬 GAAP + IFRS를 둘 다 깊게 아는 희소 시니어" → 도구로 민주화.
- **삼일에게의 의미:** 저마진 감사 방어가 아니라 **고마진 지식자문의 레버리지(1인당 산출)↑ + 희소 전문가 의존↓**. (전략 근거: `SUBMISSION_QUESTIONS.md`)

## 1. 범위 (A → B)

- **A (코어·데모): K-GAAP(일반기업회계기준) → K-IFRS.** IPO 상장전환 수요. 공개 코퍼스 짙음. **먼저 완성.**
- **B (확장·핵심가치): 해외 자회사 로컬 GAAP → K-IFRS 연결. 다국가.** 시작 = **베트남(VAS)**. 이후 DART 분석으로 정한 우선순위 국가 순차 추가.
- **아키텍처 원칙: corpus-pluggable.** 소스 GAAP은 "코퍼스 + 매핑 규칙"을 갈아끼우는 플러그로 취급 → A로 증명, B로 확장.

## 2. INPUT 명세

| 항목 | 필수 | 내용 | 포맷 |
|---|---|---|---|
| 시산표(trial balance) | ✅ | (계정코드, 계정명, 금액) 전체 계정 | `.xlsx` / `.csv` |
| 메타 | ✅ | source_gaap, currency, period | 입력값/헤더 |
| 소스 재무제표(BS/PL) | 선택 | 대조·표시용 | `.xlsx` |
| Layer 2 보조자료 | 선택 | 리스계약·채권연령·평가 등(있으면 해당 조정 자동화) | `.xlsx`/`.csv` |

**XBRL은 input이 아니다** — 대상(비상장·해외자회사)은 전환 前이라 DART XBRL이 존재하지 않는다. XBRL/DSD는 상장 제출용 **출력 확장 옵션**으로만.

**1차 처리 = canonical schema 정규화** (지저분한 실제 파일 → 내부 표준 JSON):
```json
{ "source_gaap":"K-GAAP", "currency":"KRW", "period":"2025-12-31",
  "accounts":[ {"code":"...","name_src":"개발비","amount":1200000000}, ... ] }
```
→ **Codex 핵심 역할:** 파일마다 다른 포맷(한국어·베트남어 계정명, 제각각 양식)을 매번 적응형 파싱코드로 흡수(정적 매크로가 못 하는 지점).

## 3. OUTPUT 명세 (3종)

| # | 산출물 | 내용 | 포맷 |
|---|---|---|---|
| ① | **IFRS 재무제표** | K-IFRS 구조 BS/PL | **Excel**(주) + JSON |
| ② | **전환조정 명세서** | 조정별: 소스계정 → IFRS처리 → 금액 → 방향(↑/↓) → 영향 IFRS계정 → **기준서 출처 인용** + confidence | **Excel**(핵심 신뢰 산출물) |
| ③ | **영향 분석** | 자산·부채·자본·순이익·주요비율의 소스 vs IFRS 델타 + "이 계정 오르고 저 계정 내리고 수익성 변화" 서술 | Excel/MD |

**포맷 결정:** Excel 주력(회계사가 검토·수정) + JSON 병행(후속 자동화). XBRL/DSD는 확장 옵션.

## 4. 처리 파이프라인

```
소스 시산표(.xlsx/.csv) ─▶ ① 파싱·정규화(canonical)
                                    │
지식 코퍼스(기준서·비교가이드) ─▶ ② 계정 매핑(Layer1) ─▶ ③ 측정조정(Layer2, 데이터 허용분)
                                    │                          │
                                    └──────────┬───────────────┘
                                               ▼
                        ④ 산출: IFRS FS + 전환조정 명세(인용) + 영향분석
```

## 5. 조정 범위 정책 (중요)

전체 GAAP 차이를 자동계산 못 하는 이유 = 시산표 크기가 아니라, **Layer 2 조정이 시산표 밖 데이터 + 판단을 요구**하기 때문. 그래서:

- **Layer 1 (재분류·매핑): 전면 자동.** 시산표만으로 가능 → 모든 계정 IFRS 표시체계로 매핑.
- **Layer 2 (인식·측정): 선택 자동 + 플래그.** v1 자동화 대상 = **고빈도·고임팩트 3~5개**: 리스(IFRS 1116), 금융상품 분류·측정(IFRS 1109), 공정가치, 개발비 자본화, 대손(ECL). 보조자료 있으면 계산, 없으면 **"추가자료·판단 필요"로 플래그.**
- **진단은 전면적(comprehensive detection):** 자동계산 못 해도 "이 영역에 IFRS 차이 발생 예상" 을 **전부 짚어준다.** → 커버리지는 넓게, 자동계산은 데이터 허용만큼.

## 6. 지식 / RAG 아키텍처

**벡터DB 우선 아님.** (Milvus=오버킬, Chroma=선택) 대신:
- **구조적 큐레이션 검색 + 에이전트 파일 탐색(DB-less)이 1차.** 회계기준은 번호로 색인된 구조(K-IFRS 1116, IFRS 1109, 일반기준 장별) → **"계정→기준 문단" 큐레이션 인덱스 + 토픽별 코퍼스 파일 grep/전문검색** = 정확한 인용. Codex가 구조화 파일을 코드베이스처럼 탐색.
- **보조(선택):** 자유텍스트 비교가이드에 한해 **DB 없는 flat-file 임베딩**(numpy 코사인) 또는 Chroma-로컬. 서버 DB 불필요 → 플러그인 이식성 유지.

**할루시네이션 방지 핵심 = 검색과 계산의 분리:**
1. **규칙 = LLM이 근거·출처와 함께 제시** (예: "IFRS 1116 문단 X").
2. **숫자 = Codex 코드가 결정론적으로 계산** (LLM이 숫자 생성 금지).
3. **근거 미확보 조정 = 계산 금지, 플래그** ("판단 필요").
→ 숫자는 지어낼 수 없고, 규칙은 항상 인용된다.

## 7. 검증 전략 (문항 5)

**IFRS 1(최초채택)은 "이전 GAAP ↔ IFRS 전환조정 명세"를 의무 공시.** → 최근 K-GAAP→K-IFRS 전환 상장사는:
- 마지막 K-GAAP 감사보고서(= 우리 input)
- 첫 K-IFRS 재무제표의 **전환조정 주석(= 우리 output 정답)**

둘 다 DART 공개 → **실제 published 정답셋으로 엔진 검증.** 정상케이스(전환사 재현) + 예외케이스(근거 없는 조정 → 플래그 확인).

## 8. 기능 목록

**v1 (해커톤):**
1. 입력 파서/정규화 (Excel·CSV → canonical, 한국어; 베트남어 확장 훅)
2. 계정 매핑 (Layer 1 전면) + 매핑 인덱스
3. 측정 조정 엔진 (Layer 2 고빈도 3~5개)
4. 전환조정 명세(브릿지) + 출처 인용
5. 영향 분석
6. 근거기반 검색(구조적 RAG) + 미근거 플래그
7. 산출물 렌더(Excel/JSON)

**향후:** 베트남 VAS 코퍼스, 다국가 확장, XBRL/DSD 출력, 챗봇 인터페이스, 연결 정산(다자회사 매핑).

## 9. 비범위 (Out of scope, v1)
