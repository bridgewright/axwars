# alfboard — AI 상담 에이전트 도입 준비 자동화

배포 담당자가 고객사 현업을 **음성으로 인터뷰**하면, 그 대화 한 번에서 **고객 경영진용 배포 계획서**와 **본사 프로덕트팀용 제품 인풋 문서**를 자동으로 뽑아 주는 Claude Code / Codex 플러그인. 인터뷰 스킬(`interview`)이 대화를 배포 결정 데이터(`deployment-discovery.json`) 계약으로 정리하고, 리포트 스킬(`report`)이 그 계약으로 두 문서를 집필한다. 실제 배포나 시스템 연동은 하지 않는다 — 무엇을 어떻게 깔지 정하는 **도입 준비까지**가 이 도구의 몫이다.

> 채널톡의 AI 상담 에이전트 '알프(ALF)' 배포를 사례로 설계했다. 이 저장소는 해당 기업과 무관한 개인 프로젝트이며, 모든 수치는 공개 자료에 근거한다.

## 설치 & 사용

**Claude Code**

```bash
claude plugin marketplace add bridgewright/axwars
claude plugin install alfboard@axwars
```

**Codex** — 저장소 클론 후:

```bash
codex plugin marketplace add ./axwars
codex plugin add alfboard@axwars
```

설치 뒤 새 세션 또는 `/reload-plugins`로 활성화하면 슬래시로 호출된다.

- `/alfboard:interview` — 고객 현업 음성 인터뷰 → `deployment-discovery.json`
- `/alfboard:report` — discovery → `deployment-brief.md`(배포 계획서) + `product-input.md`(제품 인풋)

**빠른 시작(음성 인터뷰)** — `skills/interview/README.md` 참조. 요약: `.env`에 `ELEVENLABS_API_KEY`를 넣고 → `bash skills/interview/setup.sh`(최초 1회 설치+에이전트 생성) → `bash skills/interview/launch.sh`(로컬 브라우저 음성, 약 2초).

## 누가, 어떤 상황에서 쓰나

엔터프라이즈 고객에게 AI 상담 에이전트 도입을 이끄는 배포 담당자(CS매니저, 영업, 온보딩·인증 전문가)가 쓴다. 고객이 상담 응대를 넘어 주문 조회나 취소 같은 실제 업무까지 맡기는 자동화를 도입하기 직전, 링크를 받은 고객사의 CS 리더, 경영진, 현장 상담사, IT 담당이 각자 음성 인터뷰에 답하면 네 관점이 하나의 데이터로 모인다.

이 배포는 자동화 범위 스코핑, 지식 정비, 시스템 연동, 변화관리, 지표 설계를 한꺼번에 다루는 IT 컨설팅형 작업이다. 담당자는 고객마다 이 조사를 백지에서 반복하고, 정작 현장에서 배운 고객 페인과 니즈는 본사 프로덕트로 환류되지 못한다. 그래서 배포는 느리고 제품은 현장을 놓친다 — 이 도구는 그 두 문제를 인터뷰 한 번으로 함께 푼다.

## 왜 이 문제인가

채널톡은 무료 도달 고객 24만 사로 저변은 이미 포화지만, 재무적으로는 2025년 말 완전 자본잠식 상태다. 다음 성장은 고객 수가 아니라 고객당 단가에서 나와야 하고, 그 단가는 구조적으로 엔터프라이즈에 몰린다. 엔터프라이즈를 여는 열쇠가 실제 업무를 대신하는 자동화(알프v2)인데, 이 자동화를 고객에 맞게 배포하는 일은 여러 이해관계자로부터 정보를 수집·정리해 본사와 논의하는 작업이라 시간이 오래 걸린다. 결국 매출 확장이 무거운 배포 인력과 조직에 비례하게 된다.

음성 에이전트로 여러 이해관계자 인터뷰를 동시에 진행하고 결과를 자동으로 문서화하면, 훨씬 적은 배포 인력으로 배포 기간을 단축할 수 있다. 현장별로는: 배포 담당자는 고객마다 현황·병목·시스템·지식 준비도를 처음부터 캐묻고 대화를 문서로 옮기는 데 시간을 쓰고, 고객사 현업은 "무엇이 문제냐"는 질문에 형용사로만 답해 스코핑에 필요한 구체 일화와 숫자가 빠지며, 본사 프로덕트팀은 배포 현장의 생생한 페인을 전해 듣지 못해 로드맵이 늦는다. 상담 자동화를 도입하는 이커머스·서비스 기업 전반에서 같은 병목이 반복된다.

## 어떻게 작동하나

```
[고객 4개 그룹]  ──ElevenLabs 음성(브라우저 WebRTC)──▶  interview  (launch.sh 한 번, ~2초)
 CS리더·경영진                                          ├ 인터뷰어가 첫 질문으로 역할을 스스로 확인 → 역할별 심층 인터뷰 흐름
 ·상담사·IT                                             ├ 4롤 × 3축(업무·병목 / 시스템·연동 / 성과·임팩트) 슬롯 채움
                                                        └ transcript → deployment-discovery.json (validate 게이트)
                                                                │
                                                                ▼  report (두 문서 모두 에이전트가 포맷 레퍼런스대로 집필)
                                                        ├▶ deployment-brief.md   (배포 계획서: 고객 C레벨용, 7섹션)
                                                        └▶ product-input.md      (제품 인풋: 본사 프로덕트팀용, 고객 페인/니즈 + 제품 고려사항)
```

- **인터뷰 방식**: 인터뷰어는 고정 질문지가 아니라 채울 빈칸을 목표로 삼는다. 페인을 대놓고 묻지 않고 어제 있었던 실제 한 장면부터 꺼내게 한 뒤 빈도 → 왜 아직 자동으로 안 넘겼나 → 원하는 것 순으로 파고든다. 데이터의 필드와 규칙은 스키마 파일 한 곳에 정본으로 두어, 인터뷰·검증·집필이 같은 계약을 따른다.
- **판단 기준**: 연동 난이도가 자동화 상한을 가른다. 업무마다 `no_integration`/`workflow`/`system_task` 중 어느 단계인지로 해결 가능 범위를 판정한다(배포 계획서 5장이 이를 진단). 성과 지표는 자동해결률 단독이 아니라 재인입률, 응답시간, 인력, 상담 만족도 묶음으로 본다. 원가는 가정 파일(`costing-assumptions.md`)과 인터뷰가 캐낸 공수로 산출한다.
- **정보 부족 시**: 원칙은 추측 금지. 확보 못 한 슬롯은 상상하지 않고 `"unknown"` 또는 `open_questions`로 남긴다. 두 번 되물어도 두루뭉술하면 그 자리를 비우고 다음으로 넘어간다. discovery가 스키마 검증에 실패하면 집필을 거부하고 인터뷰 보강으로 되돌린다.
- **데모**: discovery 없이 `report`를 부르면 새로 쓰지 않고 예시 산출물(`samples/무브온/`)을 보여줄지 먼저 묻는다 — 처음 쓰는 사람이 한눈에 흐름을 본다.

## 어떻게 검증했나

- **입력→결과 예시**: 가상 패션 이커머스 '무브온'을 예시로 CS 리더·경영진·상담사·IT 네 그룹 아홉 명의 인터뷰 대화를 입력하면, 배포 결정 데이터로 정리되고 여기서 배포 계획서와 제품 인풋 두 문서가 나온다(`samples/무브온/` 전체 동봉). 단일 역할 최소 입력 예시는 `skills/interview/assets/sample-discovery.json`.
- **정상·예외 확인**: 데이터 계약을 결정적 코드로 검증한다. 필수 키 누락, 잘못된 연동 단계나 갭 태그 값, 빈 배열 경고를 자동 테스트로 확인했고, 잘못된 값을 일부러 넣어 문서 집필이 실제로 거부되는지, 미확보 슬롯이 '확인 필요'로 표기되는지도 점검했다.
- **라이브 실행**: 브라우저 음성 인터뷰가 약 2초 만에 뜨고 에이전트가 역할부터 묻는 것을 실측으로 확인했다.
- **남은 한계**: 실제 고객 대신 가상 사례로 검증해, 진짜 배포 현장 데이터로 보정이 필요하다. 두 문서는 결정적 렌더가 아니라 에이전트 집필이라, 포맷 레퍼런스 준수로만 품질을 관리하는 한계가 있다.

```bash
# discovery 검증 데모
python3 skills/interview/scripts/validate_discovery.py skills/interview/assets/sample-discovery.json
# 테스트
python3 -m pytest skills/interview/tests -q
```

## 설계 노트

- **AI에 맡긴 것**: 음성 인터뷰 진행(ElevenLabs + LLM), 대화에서 discovery 슬롯 채우기, 두 문서를 각 포맷 레퍼런스(`references/deployment-brief-format.md`, `references/product-input-format.md`)대로 집필하는 일. 공통 작성 원칙은 두괄식, 명사형, 짧은 문장.
- **사람/코드가 맡은 것**: 자동화 범위와 연동 스코핑 판단은 배포 담당자, 계약 검증(`validate_discovery.py`)은 표준 라이브러리만 쓰는 결정적 코드(LLM 비의존). AI 저작(서사)과 결정적 계약(스키마·검증)을 분리해 재현성과 품질을 함께 확보했다.
- **막힌 지점과 해결**: 첫 실행이 파일 일곱 개를 뜯어보고 도구를 스무 번 넘게 호출하며 느렸다. 원인은 역할 플레이스홀더를 매 실행 치환해 에이전트를 고쳐야 하는 설계였고, 인터뷰어가 역할을 스스로 묻게 바꿔 치환을 없애고 실행 스크립트 하나로 통일했다. 도구 호출 27회 → 2회, 콜드 스타트 약 2초. 무거운 음성 의존성을 제거해 설치도 0.4초로 줄였다.
- **채택하지 않은 대안**: ① 두 번째 문서를 기능 명세서로 만들자는 안 — 배포 담당자는 기능을 처방하지 않으므로 고객 페인/니즈 문서로 포지션. ② CLI 안에서 인터뷰를 진행하자는 안 — WebRTC(에코 제거·끼어들기)가 없어 브라우저 필수.

## 구조

- `skills/interview/` — 음성 인터뷰(launch.sh, 역할 자기확인 4롤) → `deployment-discovery.json`
- `skills/report/` — discovery → 두 문서(배포 계획서, 제품 인풋; 에이전트가 포맷 레퍼런스대로 집필)
- `commands/` — `/alfboard:interview`, `/alfboard:report` 슬래시 커맨드
- `samples/무브온/` — 4개 그룹 9인 인터뷰 → discovery → 두 문서 완성 예시
