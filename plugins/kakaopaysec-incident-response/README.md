# kakaopaysec-incident-response — 전자금융사고 대응 문서 자동화

전자금융사고(전산장애·침해사고·전자금융사기) 발생 직후, 담당자가 규제 시한 안에 만들어야 하는 보고·공지·신고 문서를 **사고 사실 입력 한 번으로 자동 생성**하는 Claude Code / Codex 플러그인. 금감원 사고보고서는 공식 서식(별지 제2호서식) 그대로 표지까지 붙은 PDF로 나온다. 인프라 복구나 감독원 시스템 자동 제출은 하지 않는다 — 곧바로 제출·게시할 수 있는 **'제출 직전 문서'까지**가 이 도구의 몫이다.

> 카카오페이증권을 사례 기업으로 설계했지만, 회사 정보와 판정 임계값은 `shared/company.json`으로 외부화되어 있어 다른 금융회사 정책에 맞춰 조정할 수 있다. 이 저장소는 해당 기업과 무관한 개인 프로젝트이며, 모든 수치와 규정은 공개 자료에 근거한다.

## 누가, 어떤 상황에서 쓰나

CISO 조직·비상연락 담당자(규제 보고), 컴플라이언스(유출 신고·이사회 상정), 고객대응팀(공지)이 같은 사고 정보를 공유하며 함께 쓴다. MTS 먹통, 체결 지연, 해킹, 정보 유출이 터진 직후 — 사고를 인지한 순간부터 금감원 24시간, 유출 신고 72시간 시한이 도는데, 정작 대응은 야간이나 주말에 소수 인력이 맡는 경우가 많다.

담당자가 막히는 지점은 세 곳이다.

1. **보고 대상 판단** — "이게 금감원 보고 대상인가"를 중단 30분, 이용자 1만명 같은 임계 기준으로 규정에서 찾아 판단해야 한다.
2. **병행 신고 누락** — 침해사고면 KISA 신고, 중대 사고면 이사회 보고처럼 금감원 보고로 갈음되지 않는 신고를 놓치기 쉽다.
3. **동시 다발 문서 작성** — 별지 제2호서식, 정보주체 통지문, 이사회 보고서를 백지에서 동시에 써야 한다.

이 반복 작업에서 공지 시점 불일치, 원인 누락, 보고 지연이 생긴다. 플러그인은 진입점 스킬이 4개 문항으로 사고를 분류해 시한 기준 대응 순서를 안내하고, 각 산출물의 판정과 초안을 제출 직전 단계까지 자동으로 끌어올린다. 실제 제출·발송·복구는 사람의 몫이다.

## 왜 이 문제인가

카카오페이증권의 MTS 전산장애는 2022년 4건 → 2023년 9건 → 2024년 11건 → 2025년 13건으로 4년 연속 증가해 누계 42건이다. 조사 대상 12개 증권사 중 유일하게 매년 늘었고, 2026년 1분기에도 5건으로 단독 최다다. IT 투자는 연평균 약 395억원으로 장애 0건인 미래에셋(1,585억원)의 1/4 수준이다. 즉 사고는 구조적으로 계속 난다.

그렇다면 승부처는 사고가 터진 뒤다. 예방(인프라)은 대규모 투자와 시간이 필요하고, 복구와 실제 제출은 사내 시스템과 사람의 몫이라 자동화 여지가 좁다. 공개된 규정과 서식만으로 정확하게 표준화할 수 있는 지점은 하나 — **시한 안에 보고·공지·신고 문서를 백지에서 만들어내는 일**이고, 이 플러그인은 정확히 그 지점만 다룬다.

담당자는 24시간/72시간 시한 속에서 규정 해석과 서식 작성을 동시에 해야 해 백지와 시간 압박에 걸리고, 고객은 '정상화 공지 후에도 미복구'(2025년 10월 한 달 4회 장애)로 매매 기회를 놓치며, 감독당국은 반복 장애에 2026년 4월 IT 부문 현장점검에 착수했다. 토스증권도 42건으로 공동 최다일 만큼 핀테크 증권사 전반에서 장애가 늘어, 대응을 표준화할 수요가 크다.

## 구성 — 진입점 1 + 대응 스킬 5 + 공통 유틸

모든 스킬은 공통 데이터 모델 [`shared/incident.schema.json`](shared/incident.schema.json)(`incident.json`)을 공유한다. 한 번 입력한 사실이 모든 산출물에 일관되게 흐른다. 산출물은 항상 `.md`(+PDF)로 `<incident 폴더>/out/`에 자동 저장된다.

| 스킬 | 디렉터리 | 산출물 | 근거 |
|---|---|---|---|
| **진입점** 사고 대응 시작 | `skills/incident-response` | 트리아지 + 조건부 대응 순서 안내 + 하위 스킬 호출 | 오케스트레이터 |
| 1. 금감원 사고보고서 | `skills/regulator-incident-report` | 별지 제2호서식 초안(최초/중간/종결) + EFARS 필드블록 + **공식 PDF**(표지+별첨1) | 전자금융감독규정 시행세칙 제7조의4 |
| 2. 고객 공지문 | `skills/customer-outage-notice` | 실시간/복구, 3채널(홈피·MTS·알림톡) | 약관·소비자보호 |
| 3. 경영진·이사회 보고서 | `skills/exec-board-report` | 경영진 속보 / 이사회 보고서 + 보고대상 자동판정 + 병행신고 | 전자금융감독규정(2025.8.5)·지배구조법 |
| 4. 개인정보 유출 신고 | `skills/privacy-breach-filing` | 정보주체 통지문 + 감독기관 신고서 + 72h 시한 + 신용정보법 이원신고 | 개인정보보호법 §34·시행령 §40, 신용정보법 §39조의4 |
| 5. 대응 시한 대시보드 | `skills/response-deadline-tracker` | 규제 시한 D-counter(금감원 24h·KISA 24h·유출 72h·보상 14영업일) | 보고 단계별 deadline |

> **보상 산정은 스킬에서 제외했다.** 보상액 계산은 수천 건 주문·체결 데이터 배치 연산으로 사내 OMS/정산 시스템의 몫이며 예외 케이스가 많아 대화형 스킬에 부적합하기 때문. 단 보상 통지 **기한**(접수+14영업일)은 response-deadline-tracker가, 보상 **안내 문구**는 customer-outage-notice가 담당한다.

**공통 유틸 (`shared/scripts/`)**

- `run_all_skills.py` — 한 사건에 전 스킬 일괄 실행(사전검증 → 6스킬 → 정합성 검증)
- `form_mapping.py` — 별지 서식 체크박스 매핑의 단일 원천(md·PDF·검증기 공용)
- `validate_incident.py` — 실행 전 스키마 enum·필수필드 사전 검증(각 스킬 내장)
- `verify_fss_consistency.py` — incident.json ↔ md ↔ PDF 3자 정합성 가드레일
- `set_status.py` — 산출물 생성/제출 후 `reporting{}` 상태 write-back(대시보드 정확도)
- `new_incident.py` — 빈 incident.json 스켈레톤 생성

**데이터 모델** — 스키마 필드는 별지 제2호서식 항목에 맞춰 설계했다. 예시 입력은 [`shared/incident.example.json`](shared/incident.example.json)(2025.10.8 DriveWealth 연계 장애 기반).

## 작동 방식

**절차** — 진입점 스킬 `incident-response`가 사고유형·복구여부·개인정보 동반·규모 4개 문항으로 사고를 분류하고, 단일 사실 원장 `incident.json`을 만든 뒤, 시한 기준 조건부 순서로 5개 스킬을 호출한다: 고객 실시간공지=즉시, 금감원 보고=24h, 병행신고=조건부, 이사회 보고=중대 시, 복구공지·종결·보상=복구 후, 대시보드=상시.

**지식** — 전자금융사고를 적용 법률과 규제에 따라 겹치지 않고 빠짐없이 14가지 유형으로 나눴다. 크게 전산장애, 침해사고, 전자금융사기, 복합사고로 갈려 어떤 사고든 하나로 분류된다.

**판단 기준** — 판정은 법 조문 단위로 코드화했다. 금감원 보고 대상 = 지연·중단 30분 이상 또는 10분 이상+이용자 1만명(시행세칙 제7조의4), 제외 = 1개 영업점·공개웹서버·사기 100만원 미만·3억원 미만 일괄. 유출 신고 = 1천명 이상/민감·고유식별정보/외부침해(개인정보보호법 시행령 제40조). 이사회 중대성 = 필수사유(침해·개인정보) 또는 가중요인 2개 이상. 병행 신고 = 정보통신망법 제48조의3(KISA 24h)·신용정보법 제39조의4. 임계값은 `company.json`으로 외부화했다.

**정보가 부족하거나 안 풀릴 때** — 원칙은 추측 금지. 값이 불확실하면 0이 아니라 '미상'(`null`)으로 두고, 스크립트가 "임계 재판정 필요" 경고를 붙인다(구간 중앙값으로 30분·1만명 임계를 넘겨짚지 않는다). 실행 전 `validate_incident`가 형식과 필수 항목을 검증해 오류면 생성을 중단하고, 만든 뒤에는 `verify_fss_consistency`가 입력·화면·PDF의 3자 일치를 검증한다. 헤드리스 브라우저가 없으면 PDF 대신 HTML을 저장하고 '인쇄로 PDF' 안내로 대체한다. 복구 전(`resolved_at` 미확정)이면 '정상화' 공지와 종결보고를 잠가 성급한 발표를 막는다.

## 어떻게 검증했나

**입력→결과 예시** — 2025.10.8 DriveWealth 연계 장애를 `incident.json`으로 입력(외부요인·중단 17분·규모 미상)하면, 금감원 보고 **'비대상'**(17분<30분, 규모 미상이라 '1만명 재판정 필요' 경고) + 고객 실시간공지 생성 + 병행신고 없음(개인정보 무관) + 이사회 비대상으로 갈린다. 반대로 블루오션 ATS 사태(중단 지속·외부 제3자+타사 동시영향)는 이사회 **'대상'**(가중요인 2개)으로 갈린다.

**정상·예외 확인** — 현행 법령상 구분되는 14종 시나리오 판정을 기대값과 대조해 **14/14 일치**. 공개 정보로 유형을 복원할 수 있는 실제 장애 8건을 재현해 보고 대상 5건, 비대상 3건, 이사회 대상 1건(블루오션)을 확인했다. 예외는 필드 누락, enum 위반, 미상(null), 복구 전, 브라우저 부재를 각각 넣어 크래시나 오판정이 없는지 봤고(**pytest 25건**), 일부러 깨뜨린 enum이 실제로 차단되는지(음성 테스트)까지 확인했다.

**테스트하며 고친 점** — 이용자 수 미상을 0명으로 표기하던 것을 '미상 + 재판정 경고'로, 금감원 보고로 갈음되지 않는 KISA 병행신고 누락을 추가로, 병행 신고를 한 줄로 뭉치던 것을 항목별 불릿으로, 경영진 보고 제목이 '전산장애'로 하드코딩돼 있던 것을 실제 사고 유형이 반영되게 고쳤다.

**남은 한계** — 개별 사건의 이용자 수와 금액이 대부분 언론에 비공개라 정확한 판정에는 회사 내부 기록이 필요하다. 정보통신망법이 증권사에 그대로 적용되는지는 법적 판단이 필요해 경고 표시까지만 뒀다.

## 설계 노트

- **AI에 맡긴 것**: 여러 에이전트를 병렬로 돌려 공개자료(국정감사·언론·법제처)를 나눠 조사하고 교차검증했다. '42건'이 개별 사건이 아니라 금감원 제출 연간 집계의 누적임을 밝힌 것도 이 대조에서 나왔다. 별지 제2호서식의 PDF 재현, 매핑 모듈·검증기의 반복 리팩터, 14종 유형의 커버리지 gap 탐색도 AI의 몫.
- **사람이 직접 판단한 것**: 예방이 아니라 '발생 직후 문서 대응'으로 문제를 좁힌 결정, 14종 시나리오를 법 조문 단위로 확정하는 커버리지 프레임, 스킬 경계(무엇을 넣고 뺄지). 진입점 스킬을 맨 앞에 둔 것도 담당자 입장에서 직접 써 보니 처음 여는 사람이 무엇부터 할지 헤매기 쉬웠기 때문.
- **막힌 지점과 해결**: ① 스킬 트리거 자동평가가 환경상 신뢰하기 어려워 서브에이전트 라우팅 테스트(22/22 통과)로 대체했다. ② 문서끼리 맞는지 보는 정합성 검증기의 자체 버그(정규식이 값셀 대신 키셀을 읽음)를 그 검증기가 오히려 드러내 바로잡았다.
- **채택하지 않은 대안**: 보상액 계산 스킬은 사내 시스템의 몫이고 예외가 많아 뺐다. 스킬 이름에 번호를 붙이는 안은 흐름이 조건부·병렬이라 1→2→3 순서로 오해될 수 있어 거절하고, 진입점 오케스트레이터 하나로 대신했다.

## 경계와 책임

- 탐지, 복구, 감독원 실제 제출, 공지 발송, 보상액 산정은 사람과 사내 시스템의 몫이다.
- 모든 산출물은 담당자 검토용 초안이며 법적 효력을 갖지 않는다.
- 정량 수치는 공개 자료 기반, 규정 판정은 법제처 현행 조문 근거이며, 미확인 값은 '미상'으로 명시한다.
