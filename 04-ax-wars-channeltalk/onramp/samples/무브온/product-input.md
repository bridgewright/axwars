# 고객 페인 → 제품 제언 — 무브온 (애슬레저 패션 이커머스)

## ⚡ 결론 먼저 — 제언

**교환·반품을 '답변'이 아니라 서버측 조건검증까지 포함한 '실제 처리'로 끝내는 액션 태스크가 최우선 제품 요구**

CS리더·상담사·IT가 공통으로 조건부 교환·반품 접수를 사람이 꼭 개입하는 지점으로 지목했고, 이는 해결률을 30%대에서 80%대로 끌어올리는 핵심이다. 더불어 짧은 질문 되묻기, 상세페이지 기반 지식 검색, 반품 사유의 타부서 유통, 결제정보 토큰화 연동이 여러 인터뷰에서 반복 신호로 나타났다.

- **신호 강도(태그별 건수)**: 실제 처리(액션/태스크) 2건, 되묻기·맥락 수집 2건, 지식 저작 자동화 2건, 상담 데이터 타부서 유통 1건, 사람 이관 품질·보안 1건, 성과 지표 재정의 1건

## 고객이 실제로 겪는 문제 (현장 인용)

> "지난 시즌오프 프로모션 때 하루 2000건 넘게 들어와서, 5명이 밤 11시까지 붙어도 다음 날 아침 300건씩 밀려 있었어요"
>
> — 대형 프로모션·라이브방송마다 (분기 1~2회), 막힌 이유: 사람을 그만큼 못 뽑고, 단기 알바는 정책을 몰라 실수가 잦아 검수에 더 손이 감

> "사이즈 교환 한 건에 주문 상태 조회·재고 확인·회수 신청·안내까지 5~7분, 하루 100건 넘으면 사람 하나가 종일 매달려요"
>
> — 상시, 환절기 급증, 막힌 이유: 재고 유무에 따라 교환/환불 분기가 갈리는데 그 판단이 시스템 값을 봐야 결정됨 — 답변만으로 불가

> "재입고 문의는 하루 수십 번 같은 답을 복붙하는데, FAQ가 단어형이라 '이거 언제 다시 들어와요' 같은 문장을 알프가 잘 못 잡아요"
>
> — 상시, 막힌 이유: FAQ가 단어 위주로 짜여 자연어 매칭이 약함

> "'이거 교환돼요'처럼 짧게만 물어오면 어떤 주문인지·왜 교환하려는지 사람이 다시 되물어야 하는데, 알프는 그걸 못하고 '확인 어렵습니다'로 넘겨버려요"
>
> — 상시, 막힌 이유: 모호한 첫 질문에 대한 되묻기·맥락 수집이 안 됨

> "소재·세탁·다림질 질문이 오면 상세페이지나 케어라벨을 매번 찾아 확인하고, 애매하면 MD에게 물어 반나절씩 늦어져요"
>
> — 상시, 막힌 이유: 소재 정보가 상품마다 정리된 위치가 달라 신입은 어디서 찾을지도 모름

> "오배송 클레임은 물류·재고 시스템을 오가며 주문번호를 복사해 붙여 조회하고 회수를 따로 넣다가 다른 주문 회수를 잘못 잡은 적도 있어요"
>
> — 하루 몇 건 (사이즈 교환은 하루 수십 건), 막힌 이유: 재고·회수 시스템이 상담 화면과 분리돼 정보를 수기로 옮겨야 함


## Problem Statement
지난 시즌오프 프로모션 때 하루 2000건 넘게 들어와서, 5명이 밤 11시까지 붙어도 다음 날 아침 300건씩 밀려 있었어요 — 반복·정형 문의가 특정 시점에 폭증하는데 실제 처리가 사람에 묶여 있다.

## Solution
- 피크에도 앞단에서 반복 문의가 자동 처리되어 인력 증원 없이 감당
- 조건(7일 이내·택 미개봉·재고 있음)을 알프가 시스템으로 판단해 교환접수까지 자동 처리
- 재입고 안내를 알프가 단독으로 처리
- 알프가 능동적으로 되물어 맥락을 확보한 뒤 처리하거나 정리해 이관
- 알프가 상세페이지에서 소재·세탁·사이즈 정보를 바로 찾아 응답
- 조회·회수 처리를 자동화해 화면 이동·복붙 제거

## User Stories
- As a 고객사 CS 담당, I want 알프가 **배송조회**를 자동 처리, so that 반복 응대를 줄이고 피크에 대응한다
- As a 고객사 CS 담당, I want 알프가 **재입고 안내**를 자동 처리, so that 반복 응대를 줄이고 피크에 대응한다
- As a 고객사 CS 담당, I want 알프가 **소재/세탁/사이즈 안내**를 자동 처리, so that 반복 응대를 줄이고 피크에 대응한다
- As a 고객사 CS 담당, I want 알프가 **주문취소**를 자동 처리, so that 반복 응대를 줄이고 피크에 대응한다
- As a 고객사 CS 담당, I want 알프가 **조건부 교환/반품 접수**를 자동 처리, so that 반복 응대를 줄이고 피크에 대응한다
- As a 고객사 CS 담당, I want 알프가 **회수/환불 처리**를 자동 처리, so that 반복 응대를 줄이고 피크에 대응한다

## Implementation Decisions
- 배송조회: `workflow` — 백엔드 택배사 조회, API yes, 개발 주체 vendor (파일·코드는 명시하지 않음)
- 재입고/소재 안내: `no_integration` — 백엔드 상세페이지·상품 DB(문서/RAG), API yes, 개발 주체 inhouse (파일·코드는 명시하지 않음)
- 주문조회/취소/교환접수: `system_task` — 백엔드 자체 커머스 백엔드(내부 REST API), API yes, 개발 주체 inhouse (파일·코드는 명시하지 않음)
- 회수 처리: `system_task` — 백엔드 외주 WMS, API yes, 개발 주체 vendor (파일·코드는 명시하지 않음)
- 환불(금액 계산): `system_task` — 백엔드 외부 PG + 쿠폰/적립금 로직, API yes, 개발 주체 vendor (파일·코드는 명시하지 않음)

## Testing Decisions
- 외부 동작(고객 요청 → 처리 결과)만 검증한다. 구현 세부는 테스트하지 않는다.
- 유사 선례: 기존 태스크 자동화(주문·교환·구독취소 등)의 종단 시나리오.

## Out of Scope
- 이번 인터뷰에서 확인되지 않은 시스템·업무(아래 '결정 필요' 참조).

## Further Notes
- 회수 외주 WMS 연동·테스트 실제 기간(2~3주 추정) 확정 및 2차 착수 시점
- 환불 금액 계산(부분환불·쿠폰·적립금) 자동화 범위와 검증 방식
- 채널톡 측 보안 지원 스펙 — 결제/개인정보 토큰화·로그·엔드포인트별 권한 분리 지원 범위
- 알프 전용 안전 엔드포인트(서버측 조건검증) 설계 합의
- 피크 시즌 일정과 1차(조회·취소·교환접수)·2차(회수·환불) 롤아웃 타이밍 정합성

## 제품 갭 — 무엇을, 왜 (태그별 우선순위)

### `[action_task]` 실제 처리(액션/태스크) — 2건
- 신호: 조건 검증까지 포함한 실제 교환·반품 접수 자동화 필요
  > "조건 맞으면 알프가 이 버튼 누르는 걸 대신해줬으면 좋겠다는 생각은 늘 해요 (한소미)"
- 신호: 교환·반품 실제 처리가 사람 개입의 핵심 지점
  > "알프가 앞단에서 접수만 받고, 결국 사람이 어드민 열어서 처리해요 (김서연)"

### `[reask_context]` 되묻기·맥락 수집 — 2건
- 신호: 짧고 모호한 질문에 능동적으로 되물어 맥락을 잡아야 함
  > "'이거 교환돼요'만 오면 어떤 상품인지 왜 교환하려는지 제가 다시 여쭤봐야 해요 (최다은)"
- 신호: v1은 모호한 질문을 '확인 어렵습니다'로 끊고 사람에게 넘김
  > "알프가 그 되묻기를 잘 못해서 그냥 확인이 어렵습니다 하고 사람한테 넘겨버려요 (박준호)"

### `[knowledge_authoring]` 지식 저작 자동화 — 2건
- 신호: 상세페이지 기반 소재·세탁 정보 검색·응답 필요
  > "소재·세탁·사이즈 정보는 알프가 상세페이지에서 바로 찾아서 답해주면 좋겠어요 (최다은)"
- 신호: FAQ 문장형 전환·지식 위치 표준화가 성능 전제
  > "FAQ가 단어 위주라 알프가 자연스러운 문장을 잘 못 잡아요 (김서연)"

### `[voc_distribution]` 상담 데이터 타부서 유통 — 1건
- 신호: 반품 사유를 유형별로 모아 기획·MD에 유통하고 싶음
  > "반품 사유를 유형별로 모아서 기획팀이랑 MD한테 넘기는 일을 하고 싶어요 (박준호)"

### `[handoff_quality]` 사람 이관 품질·보안 — 1건
- 신호: 결제·개인정보는 원문 전달 불가, 토큰화·로그·권한 분리 필요
  > "필요한 최소 필드만 마스킹·토큰화해서 주고받아야 하고 로그·권한도 나눠야 해요 (강태영)"

### `[metric_redefine]` 성과 지표 재정의 — 1건
- 신호: 자동해결률 단독 목표는 CX를 해쳐 지표 재정의 필요
  > "자동해결률 숫자에 집착하면 고객 경험을 희생하게 돼요 (이하늘)"
