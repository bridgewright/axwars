# 채널톡 프로덕트팀 전달: 무브온 배포에서 본 고객 페인포인트/니즈와 제품 고려사항

> 받는 사람: 알프 제품/로드맵 오너 (지식, 규칙, 태스크 기획과 엔지니어링)
> 목적: 이 배포에서 반복 관측된 고객 페인포인트/니즈와, 그것을 제품으로 만들 때의 고려사항 정리
> 근거: 4개 그룹 9인 인터뷰 — CS리더 2인(김서연, 박준호), 경영진 2인(이하늘, 정민재), 현장 상담사 3인(윤지아, 최다은, 한소미), IT 2인(오세훈, 강태영)

---

## 1. Summary

**이 배포가 제품팀에 주는 가장 강한 신호는 "교환과 반품을 답변이 아니라 조건 검증까지 포함한 실제 처리로 끝내는 것"임.** CS리더, 현장 상담사, IT 세 그룹이 공통으로 이 지점을 사람이 꼭 개입하는 병목으로 지목했음. 이는 알프 태스크가 이미 향하는 방향과 정확히 맞아, 그 우선순위를 현장이 뒷받침하는 셈임

그다음으로 강한 신호가 두 개 더 있음. 하나는 모호한 첫 질문에 알프가 되묻지 못해 불필요하게 사람에게 넘기는 문제이고, 다른 하나는 지식이 단어형이고 산재해 자연어 응답이 안 되는 문제임. 이 둘은 실제 처리만큼 자주 언급됐으나, 알프 태스크에 비하면 제품이 덜 성숙한 영역으로 보임

---

## 2. 고객 페인포인트/니즈 지도

**총 9건의 제품 신호가 6개 페인포인트/니즈로 묶임. 여러 그룹이 공통 지목한 실제 처리, 되묻기, 지식 저작이 상위 신호임**

- [신호 강도] 실제 처리 2건, 되묻기 2건, 지식 저작 2건, 상담 데이터 유통 1건, 이관/보안 1건, 지표 재정의 1건

| 페인포인트/니즈 | 제품 표면 | 신호(건수) |
|---|---|---:|
| 조건부 교환/반품 실제 처리 | 알프 태스크 | 2 |
| 모호한 질문 되묻기 | 알프 대화(되묻기) | 2 |
| 지식 기반 응답 + 지식 정비 | 알프 지식, 지식 저작 도구 | 2 |
| 반품 사유 타부서 유통 | 애널리틱스/리포팅 | 1 |
| 이관 시 결제/개인정보 보호 | 이관/보안 | 1 |
| 성과 지표 재정의 | 지표/대시보드 | 1 |

## 3. 페인포인트/니즈별 상세

- **[실제 처리 — 조건부 교환/반품]** 알프가 지금은 접수만 받고, 실제 처리는 사람이 어드민에서 함. 재고가 있으면 교환, 없으면 환불로 갈리는데 그 판단이 시스템 값을 봐야 결정돼 '답변'만으로 끝나지 않음
  > "조건 맞으면 알프가 이 버튼 누르는 걸 대신해줬으면 좋겠다는 생각은 늘 해요" — 상담사 한소미
  >
  > "알프가 앞단에서 접수만 받고, 결국 사람이 어드민 열어서 처리해요" — CS팀장 김서연
  - 제품 개발 시 고려사항: 조건(배송완료 7일 이내, 재고 있음, 택 미개봉)을 서버가 다시 검증하는 안전장치가 필요함. 알프가 조건을 잘못 판단해도 시스템이 막게 설계해야 함. 잘못 처리되면 돈과 재고가 걸린 문제라, 되돌리기와 검증 설계가 특히 중요함
- **[되묻기 — 모호한 첫 질문]** "이거 환불돼요"처럼 짧게만 오면 어떤 주문인지 왜 그런지 사람이 되물어야 함. 지금 알프는 그걸 못하고 "확인이 어렵습니다"로 끊어 사람에게 넘김
  > "'이거 교환돼요'만 오면 어떤 상품인지 왜 교환하려는지 제가 다시 여쭤봐야 해요" — 상담사 최다은
  >
  > "알프가 그 되묻기를 잘 못해서 그냥 확인이 어렵습니다 하고 사람한테 넘겨버려요" — CS파트리더 박준호
  - 제품 개발 시 고려사항: 능동적으로 되물어 맥락을 확보한 뒤 처리하거나, 정리해서 이관하는 흐름이 필요함. 되묻기가 없으면 앞단 필터가 실패해 오히려 이관률이 올라감. "확인이 어렵습니다"로 끊는 회피 패턴이 현장 불만의 핵심임
- **[지식 — 단어형 FAQ와 산재된 정보]** 소재와 세탁 정보를 상세페이지나 MD 확인으로 매번 찾음. FAQ가 단어형이라 문장 질문을 놓치고, 정보가 상품마다 다른 곳에 흩어져 있음
  > "소재, 세탁, 사이즈 정보는 알프가 상세페이지에서 바로 찾아서 답해주면 좋겠어요" — 상담사 최다은
  >
  > "FAQ가 단어 위주라 알프가 자연스러운 문장을 잘 못 잡아요" — CS팀장 김서연
  - 제품 개발 시 고려사항: 상세페이지 같은 원천에서 바로 찾아 답하는 능력과 함께, 지식을 문장형으로 정비하고 위치를 표준화하는 저작/온보딩 도구가 성능의 전제임. 데모는 되는데 실운영이 안 되는 지점이 대개 여기임
- **[상담 데이터 유통 — 반품 사유]** CS가 반복 응대에 묶여, 반품 사유를 모아 상류(기획, MD)로 넘기는 일을 못 하고 있음
  > "반품 사유를 유형별로 모아서 기획팀이랑 MD한테 넘기는 일을 하고 싶어요" — CS파트리더 박준호
  - 제품 개발 시 고려사항: 상담 데이터를 유형별로 모아 타부서로 흘리는 리포팅 표면이 필요함. 이는 반품률 자체를 낮추는 상류 개선으로 이어져, CS를 비용에서 매출 기여로 바꾸는 지점임
- **[이관/보안 — 결제와 개인정보]** 결제와 개인정보는 원문을 채널톡으로 넘길 수 없음. 실제 처리를 자동화하려면 이 전제가 먼저 풀려야 함
  > "필요한 최소 필드만 마스킹하거나 토큰화해서 주고받아야 하고, 기록이랑 권한도 나눠야 해요" — 백엔드 개발자 강태영
  - 제품 개발 시 고려사항: 꼭 필요한 값만 가리거나 대체해서 주고받기, 요청 기록 남기기, 기능별 권한 나누기가 실제 처리 자동화의 게이트임. 사람에게 넘길 때 맥락을 함께 보존하는 것도 필요함
- **[지표 — 자동해결률 함정]** 자동해결률 숫자에 집착하면 고객이 두세 번 되묻게 돼 오히려 경험이 나빠짐. 경영진이 이 함정을 이미 인지하고 있음
  > "자동해결률 숫자에 집착하면 고객 경험을 희생하게 돼요" — 대표 이하늘
  - 제품 개발 시 고려사항: 제품이 어떤 지표를 전면에 노출하느냐가 고객사의 운영 행동을 좌우함. 자동해결률 단독이 아니라 재인입률, 상담 만족도, 이탈 방지를 묶어 보여주는 지표 설계가 필요함

## 4. 제품 개발 간 고려사항

- **[지식 정비가 모든 기능의 전제]** 어떤 알프 기능도 지식이 단어형이고 산재하면 성능이 안 남. 지식 저작과 온보딩 도구의 완성도가 실운영 품질을 좌우함
- **[지표가 행동을 만든다]** 자동해결률만 전면에 노출하면 고객사가 그 숫자를 좇다 CX를 희생함. 지표 설계가 곧 제품이 유도하는 운영 방향임
- **[보안이 실제 처리의 게이트]** 실제 처리 자동화는 결제와 개인정보 보호 없이는 나갈 수 없음. 이 지원 범위가 곧 자동화 상한을 가름
- **[로드맵 관계]** 알프v2 태스크는 실제 처리 방향을 이미 향하고 있어, 이 고객 신호가 그 우선순위를 뒷받침함. 반면 되묻기, 지식 저작, 상담 데이터 리포팅은 상대적으로 덜 성숙해 보완 여지가 큼
