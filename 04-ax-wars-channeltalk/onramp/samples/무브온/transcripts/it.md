# 인터뷰 트랜스크립트 — 무브온 · 그룹: IT/시스템 담당 (2명)

> 격식체. 인터뷰이: 개발리드 오세훈, 백엔드 개발자 강태영.

---

## 1) 개발리드 오세훈

**인터뷰어:** 안녕하세요. 시간 내주셔서 감사합니다. 지금 주문이나 회원, 재고 관련해서는 어떤 시스템을 쓰고 계신가요?

**오세훈:** 크게 세 덩어리예요. 주문·회원·상품 관리는 저희가 자체 구축한 커머스 백엔드에서 돌고요, 결제는 외부 PG를 붙여 씁니다. 물류랑 회수는 외주 WMS 솔루션을 쓰고 있어요. 상담사분들이 보시는 어드민은 이 커머스 백엔드 위에 얹힌 내부 화면이에요.

**인터뷰어:** 그 시스템들이 하나로 통합되어 있나요, 아니면 나뉘어 있나요?

**오세훈:** 주문·회원·상품·재고는 저희 백엔드 하나로 통합돼 있어요. 그래서 주문 상태 조회나 재고 확인, 주문 취소, 교환 접수 같은 건 저희 시스템 안에서 다 돼요. 문제는 회수예요. 회수는 외주 WMS로 요청을 던져야 하는데, 거기는 저희가 마음대로 못 고쳐요. 결제 취소·환불도 PG 규격을 타야 하고요.

**인터뷰어:** 외부에서 프로그램으로 호출할 수 있는 창구, 즉 API가 제공되나요? 문서화는 되어 있나요?

**오세훈:** 자체 백엔드는 내부 REST API가 잘 갖춰져 있어요. 주문 조회, 재고 조회, 주문 취소, 교환 접수 엔드포인트가 다 있고 문서화도 돼 있습니다. 채널톡이 이걸 호출하도록 열어드리는 건 크게 어렵지 않아요. 인증 토큰 발급하고 필요한 엔드포인트만 화이트리스트로 열면 되니까, 저희 쪽 작업은 한 일주일이면 될 것 같아요.

**인터뷰어:** 회수나 환불 쪽은 어떠신가요?

**오세훈:** 거기가 관건이에요. 회수는 외주 WMS API 규격에 맞춰야 하는데, 그쪽 문서가 오래됐고 담당자를 통해야 해서 연동 개발이랑 테스트까지 2~3주는 봐야 해요. 환불 금액 계산은 쿠폰·적립금·부분환불이 얽혀서 로직이 복잡하고, 잘못되면 돈 문제라 검증을 빡세게 해야 해요. 그래서 저라면 조회·취소·교환접수부터 열고, 회수·환불은 2차로 붙이는 걸 추천해요.

---

## 2) 백엔드 개발자 강태영

**인터뷰어:** 태영님, 고객이나 주문 정보를 연동하실 때 걸리는 보안이나 권한 이슈가 있으신가요?

**강태영:** 있어요. 개인정보랑 결제정보는 규제가 있어서, 채널톡으로 원문 데이터가 통째로 넘어가면 안 돼요. 예를 들어 카드번호나 전체 주소 같은 건 넘기면 안 되고, 꼭 필요한 최소 필드만, 그것도 마스킹하거나 토큰화해서 주고받아야 해요. 그리고 어떤 요청이 언제 들어와서 무슨 값을 조회했는지 로그를 다 남겨야 하고, 접근 권한도 엔드포인트별로 나눠야 해요.

**인터뷰어:** 알프가 교환 접수 같은 실제 처리를 하려면, 그쪽에서 무엇을 열어 주시거나 만들어 주셔야 할 것 같으신가요?

**강태영:** 조회 계열은 기존 API 그대로 쓰면 되고요, 처리 계열, 그러니까 주문 취소나 교환 접수는 알프 전용으로 안전장치를 건 엔드포인트를 하나 더 만드는 게 나아요. 예를 들어 교환 접수는 '배송완료 7일 이내, 재고 있음, 택 미개봉' 같은 조건을 서버에서 한 번 더 검증하게 해서, 알프가 조건을 잘못 판단해도 시스템이 막게요. 그 검증 로직을 저희가 API 안에 넣어두면 알프는 그냥 호출만 하면 돼요.

**인터뷰어:** 그 작업은 얼마나 걸릴 것 같으신가요?

**강태영:** 조회랑 취소·교환접수용 안전 엔드포인트는 한 2주면 만들어요. 회수 WMS 연동이랑 환불 계산은 아까 리드님 말씀처럼 별도로 2~3주 더 봐야 하고요. 그리고 채널톡 쪽에서 토큰화랑 로그, 권한 분리를 어디까지 지원해주는지 스펙을 받아야 저희가 맞출 수 있어요. 그게 정리 안 되면 보안 검토에서 막힐 수 있어요.

**인터뷰어:** 두 분 말씀 잘 들었습니다. 조회·취소·교환접수는 자체 API로 비교적 빠르게, 회수·환불은 외주 WMS·PG 때문에 2~3주 추가, 보안은 토큰화·로그·권한 분리가 전제라는 점 정리하겠습니다. 감사합니다.
