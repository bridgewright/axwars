# alfboard — 채널톡 알프 도입 준비 자동화

채널톡 배포 담당자가 고객사 현업을 **음성으로 인터뷰**하면, 그 대화 한 번에서 **고객 경영진용 배포 계획서**와 **본진 프로덕트팀용 제품 인풋 문서**를 자동으로 뽑아 주는 Codex / Claude Code 플러그인. 인터뷰 스킬(`interview`)이 대화를 배포 결정 데이터(`deployment-discovery.json`) 계약으로 정리하고, 리포트 스킬(`report`)이 그 계약으로 두 문서를 집필한다. 실제 배포나 시스템 연동은 하지 않고, 무엇을 어떻게 깔지 정하는 **도입 준비**까지가 이 도구의 몫.

---

## 심사 5문항

### 1. 무엇을, 누가, 어떤 상황에서 쓰나요? (800자 이내)

**[무엇을]** 채널톡 배포 담당자가 고객사 현업을 음성으로 인터뷰하면, 그 대화 한 번에서 두 문서를 자동으로 뽑아 주는 Codex 플러그인. 하나는 고객 경영진에게 낼 배포 계획서, 다른 하나는 채널톡 본진 프로덕트팀에 낼 고객 페인포인트와 니즈 정리 문서. 인터뷰 skill(interview)이 대화를 배포 결정 데이터 파일로 정리하고, 리포트 skill(report)이 그 데이터로 두 문서를 집필. 실제 배포나 시스템 연동은 하지 않고, 무엇을 어떻게 깔지 정하는 도입 준비까지가 이 도구의 몫.

**[누가]** 채널톡에서 엔터프라이즈 고객에게 알프(AI 상담 에이전트) 도입을 이끄는 배포 담당자. CS매니저, 영업, 온보딩과 인증 전문가가 같은 인터뷰 결과를 공유하며 사용.

**[어떤 상황에서]** 고객이 알프v2, 곧 상담을 넘어 주문 조회나 취소 같은 실제 업무까지 맡기는 자동화를 도입하기 직전. 링크를 받은 고객사의 CS 리더, 경영진, 현장 상담사, IT 담당이 각자 음성 인터뷰에 답하면 네 관점이 한 데이터로 모임.

**[어디서 막혀]** 알프v2 배포는 자동화 범위 스코핑, 지식 정비, 시스템 연동, 변화관리, 지표 설계를 한꺼번에 다루는 IT 컨설팅형 작업. 담당자는 고객마다 이 조사를 백지에서 반복하고, 정작 현장에서 배운 고객 페인과 니즈는 본진 프로덕트로 환류되지 못함. 그래서 배포는 느리고 제품은 현장을 놓침.

### 2. 왜 이 문제를 선택했나요? (800자 이내)

**[문제를 고른 이유]** 채널톡은 무료 도달 고객 24만 사로 도달은 이미 포화지만, 2025년 말 완전 자본잠식 상태. 다음 성장은 고객 수가 아니라 고객당 단가에서 나와야 하고, 그 단가는 구조적으로 엔터프라이즈에 몰림. 엔터프라이즈를 여는 열쇠가 알프v2, 곧 실제 업무를 대신하는 자동화. 그런데 이 자동화를 고객에 맞게 까는 배포는 여러 이해관계자로부터 배포에 필요한 다양한 정보를 수집하고 정리해 본사에 전달 후 논의하는 작업이기 때문에 많은 시간이 소요. 결국 채널톡은 매출 확장을 위해 이에 비례하는 무거운 배포 인력, 조직에 의존해야 하는 상황 발생. 보이스 에이전트를 통해 여러 이해관계자와의 인터뷰를 동시 진행, 본사에 자동 보고하여 배포간 병목을 최종적으로 제거 가능하며 이를 통해 훨씬 더 적은 배포 인력으로 더 빠르게 배포 기간을 단축해 채널톡의 엔터프라이즈 시장 GTM 효과 극대화 가능.

**[직원·고객·산업이 어디서 왜 막히나]** 배포 담당자는 고객마다 현황, 병목, 시스템, 지식 준비도를 처음부터 캐묻고 그 대화를 문서로 옮기는 데 시간을 씀. 고객사 현업은 무엇이 문제냐는 질문에 형용사로만 답해, 스코핑에 필요한 구체 일화와 숫자가 빠짐. 본진 프로덕트팀은 배포 현장의 생생한 페인을 전해 듣지 못해 로드맵이 늦음. 상담 자동화를 들이는 이커머스와 서비스 기업 전반에서 같은 병목.

### 3. 플러그인은 어떻게 작동하나요? (1000자 이내)

**[절차]** 스킬 두 개로 이어짐. 인터뷰 스킬은 실행 스크립트 하나로 로컬에서 브라우저 음성 인터뷰를 띄움. 고객사 현업이 ElevenLabs 음성 에이전트와 한국어로 대화하면, 인터뷰어가 첫 질문으로 상대의 역할이 CS 리더인지 경영진인지 상담사인지 IT인지 확인하고 그 역할 흐름으로 진행. 대화가 끝나면 그 내용을 배포 결정 데이터 파일로 정리. 이어 리포트 스킬이 그 데이터로 두 문서를 집필. 배포 계획서는 고객 경영진용 7개 섹션, 제품 인풋 문서는 본진 프로덕트팀용으로 고객 페인과 제품 고려사항.

**[지식]** 인터뷰어는 고정 질문지가 아니라 채울 빈칸을 목표로 삼음. 세 축, 곧 업무와 병목, 시스템과 연동, 성과와 임팩트로 묶인 슬롯을 대화로 채움. 페인을 대놓고 묻지 않고 어제 있었던 실제 한 장면부터 꺼내게 한 뒤 빈도, 왜 아직 자동으로 안 넘겼나, 원하는 것 순으로 파고드는 방식. 데이터의 필드와 규칙은 스키마 파일 한 곳에 정본으로 두어, 인터뷰와 검증과 집필이 같은 계약을 따름.

**[판단 기준]** 연동 난이도가 자동화 상한을 가름. 업무마다 연동 없음, 워크플로, 시스템 처리 중 어느 단계인지로 해결 가능 범위를 판정. 성과는 자동해결률 단독이 아니라 재인입률, 응답시간, 인력, 상담 만족도 묶음으로 봄. 원가는 가정 파일과 인터뷰가 캐낸 공수로 산출.

**[정보가 부족하거나 안 풀릴 때]** 원칙은 추측 금지. 확보 못 한 슬롯은 지어내지 않고 미상이나 미해결 질문으로 남김. 두 번 되물어도 두루뭉술하면 그 자리를 비우고 다음으로 넘어감. 데이터가 스키마 검증에 실패하면 문서 집필을 거부하고 인터뷰 보강으로 되돌림.

### 4. AI를 어떻게 썼나요? (800자 이내)

**[AI에게 맡긴 것]** 여러 AI를 함께 돌려 채널톡의 사업 모델과 재무, 알프v2 전환을 나눠 조사하고 서로 대조해 문제에 도달. 실행 단계에서는 ElevenLabs와 Claude로 음성 인터뷰를 진행하고, 대화에서 배포 결정 데이터 슬롯을 채우며, 배포 계획서와 제품 인풋 두 문서를 각 포맷 규칙대로 집필하는 일을 맡김.

**[직접 판단한 것]** 예방이나 영업이 아니라 배포 준비로 문제를 좁힌 결정. 두 번째 산출물을 기능 명세가 아니라 고객 페인과 제품 고려사항 문서로 포지션한 것. 자동화 범위와 연동 스코핑 판단. 데이터 계약 검증은 AI가 아니라 규칙을 담은 결정적 코드로 처리해, AI 저작과 계약 검증을 분리.

**[막힌 지점과 해결]** 첫째, 스킬이 슬래시로 안 떠서, 스킬만으로는 메뉴에 안 뜨고 커맨드 파일이 있어야 함을 확인해 해결. 둘째, 첫 실행이 파일 일곱 개를 뜯어보고 도구를 스무 번 넘게 부르며 오래 걸림. 원인이 역할을 매 실행 치환해 에이전트를 고쳐야 하는 설계임을 찾아, 인터뷰어가 역할을 스스로 묻게 바꿔 치환을 없애고 실행 스크립트 하나로 통일. 콜드 2초로 단축.

**[받아들이지 않은 AI 제안]** 하나, 두 번째 문서를 기능 명세서로 만들자는 제안 거부. 배포 담당자는 기능을 처방하지 않음. 둘, 시작 화면에 로고 배너 훅을 넣자는 제안 거부. 조잡하고 환경에서 렌더도 안 됨. 셋, CLI 환경 내에서 인터뷰를 진행하자는 제안 거부. WebRTC 제공하지 않기 때문에 웹 브라우저에서 인터뷰 진행 필수 이기 때문.

### 5. 어떻게 검증했나요? (800자 이내)

**[입력에서 결과 예시]** 가상 패션 이커머스 무브온을 예시로, CS 리더와 경영진과 상담사와 IT 네 그룹 아홉 명의 인터뷰 대화를 입력. 그 대화가 배포 결정 데이터로 정리되고, 여기서 배포 계획서와 제품 인풋 두 문서가 나옴. 단일 역할 최소 입력 예시도 별도로 둠. 실제 라이브 실행도 확인해, 브라우저 음성 인터뷰가 2초 만에 뜨고 에이전트가 역할부터 묻는 것을 검증.

**[정상과 예외 확인]** 데이터 계약을 결정적 코드로 검증. 필수 키 누락, 잘못된 연동 단계나 갭 태그 값, 빈 배열 경고를 자동 테스트로 확인해 통과. 잘못된 값을 일부러 넣어 문서 집필이 실제로 거부되는지 확인. 확보 못 한 슬롯이 확인 필요로 표기되는지도 점검.

**[의심한 것과 아직 부족한 것]** 실제 고객 대신 가상 사례로 검증해, 진짜 배포 현장 데이터로 보정이 필요. 두 문서는 결정적 렌더가 아니라 에이전트 집필이라, 포맷 규칙 준수로만 품질을 관리하는 한계.

**[테스트하며 고친 점]** 첫 실행이 스무 번 넘던 도구 호출을 두 번으로 줄임. 라이브 에이전트에 치환 안 된 자리표시자가 그대로 남아 소리내어 읽히던 것을, 역할 자기확인으로 근절. 무거운 음성 의존성을 빼 설치를 0.4초로 줄이고, CLI와 낡은 테스트를 정리.

## 구성 — 1개 플러그인 = 스킬 2 + 슬래시 커맨드 2 + 샘플 1

interview가 대화를 계약(`deployment-discovery.json`)으로 정리하면, report가 그 하나의 계약으로 성격이 다른 두 문서를 집필한다. AI 서사 저작과 결정적 계약 검증을 분리한 구조다.

| 구성 요소 | 디렉터리 | 무엇을 하나 | 근거 |
|---|---|---|---|
| **스킬 1 · interview** | `src/skills/interview/` | 고객 현업 음성 인터뷰(ElevenLabs, 브라우저 WebRTC) → `deployment-discovery.json` | 인터뷰어 프롬프트(SSOT) + `validate_discovery.py` 게이트 |
| **스킬 2 · report** | `src/skills/report/` | discovery → ① 배포 계획서 ② 제품 인풋 (에이전트가 포맷 레퍼런스대로 집필) | `references/` 포맷 3종 + 원가 가정 |
| **슬래시 커맨드** | `src/commands/` | `/alfboard:interview`, `/alfboard:report` (스킬 실행 진입점) | 스킬 래퍼 |
| **샘플** | `src/samples/무브온/` | 4개 그룹 9인 인터뷰 → discovery → 두 산출물 exemplar | 데모·검증 입력 |

## 스킬별 상세 동작

**스킬 1 — interview (음성 인터뷰 → 계약)**
`launch.sh` 한 번이면 venv 보장 → 에이전트 확인 → 로컬 브라우저 음성 페이지(WebRTC 에코제거로 스피커·끼어들기 동작)까지 약 2초에 뜬다. 인터뷰어는 첫 질문으로 상대의 역할(CS 리더·경영진·상담사·IT)을 스스로 확인하고 해당 흐름으로 grill-me 인터뷰를 진행한다. 페인을 대놓고 묻지 않고 어제의 구체 장면 → 빈도 → 왜 안 고쳐졌나 → 원하는 것 순으로 파고들며, 세 축(A 업무·병목 / B 시스템·연동·지식준비도 / C 성과·임팩트)의 슬롯을 채운다. 대화가 끝나면 transcript를 `deployment-discovery.json`으로 조립하고 `validate_discovery.py`로 검증한다. 확보 못 한 슬롯은 상상하지 않고 `unknown` 또는 `open_questions`로 남긴다.

**스킬 2 — report (계약 → 두 문서, 에이전트 집필)**
실제 discovery가 없거나 얇으면 곧바로 집필하지 않고, 무브온 예시 산출물을 보여줄지 먼저 묻는다(데모 폴백). 실제 discovery가 있으면 검증 후 두 문서를 에이전트가 직접 집필한다(결정론 렌더 아님). ① `deployment-brief.md`(배포 계획서, 고객 C레벨용 7섹션, 도입 우선순위 스코어링·연동 난이도·원가 포함) ② `product-input.md`(제품 인풋, 본진 프로덕트팀용 고객 페인·니즈 + 제품 개발 시 고려사항). 두 문서 모두 각 포맷 레퍼런스를 100% 지키며, 원가는 `costing-assumptions.md` 가정 기반 개략치임을 명시한다. 성과 지표는 자동해결률 단독이 아니라 재인입률·응답시간·인력·상담 만족도 묶음으로 제시한다.

## 데이터 계약 — deployment-discovery.json (SSOT)

두 스킬은 하나의 계약을 공유한다. 정본은 [`src/skills/interview/references/discovery-spec.md`](src/skills/interview/references/discovery-spec.md).

- **세 축**: A 업무·병목(`context`/`bottlenecks`/`automation_scope`) · B 시스템·연동·지식준비도(`integration`/`knowledge_readiness`) · C 성과·임팩트(`metrics`).
- **연동 tier가 자동화 상한**: 각 업무의 `tier`(`no_integration`/`workflow`/`system_task`)가 해결 가능 범위를 가른다.
- **제품 신호**: `product_gaps`의 태그(action_task·reask_context·knowledge_authoring·voc_distribution·metric_redefine·handoff_quality·multilingual·small_team)로 본진 제품 인풋을 만든다.
- **결정적 게이트**: `validate_discovery.py`가 enum·필수키·경고를 강제(LLM 비의존 stdlib). errors면 집필 거부.

## 설치 · 실행

- **Claude Code**: `claude plugin marketplace add . && claude plugin install alfboard@alfboard-dev` → `/reload-plugins` → `/alfboard:interview`, `/alfboard:report`.
- **Codex**: `codex plugin marketplace add . && codex plugin add alfboard@alfboard-dev`. `src/`가 플러그인 루트(`src/.codex-plugin/plugin.json`).
- **음성 인터뷰**: `src/skills/interview/.env`에 `ELEVENLABS_API_KEY` → `bash src/skills/interview/setup.sh`(최초 1회 설치+에이전트 생성) → `bash src/skills/interview/launch.sh`(로컬 브라우저 음성, 약 2초).
- **테스트**: `python3 -m pytest src/skills/interview/tests -q`(discovery 스키마 검증). discovery 검증 데모: `python3 src/skills/interview/scripts/validate_discovery.py src/skills/interview/assets/sample-discovery.json`.

## 샘플 산출물 (직접 실행이 어렵거나 배경지식이 없을 때)

플러그인을 직접 돌리기 어렵거나 채널톡 배포 맥락이 낯설어도, **`src/samples/무브온/` 폴더**를 열면 이 플러그인이 실제로 무엇을 만들어 주는지 바로 이해할 수 있다. 가상 패션 이커머스 무브온의 4개 그룹(CS 리더·경영진·상담사·IT) 9인 인터뷰를 입력으로 넣어 나온 산출물이다.

- `src/samples/무브온/transcripts/` — 4개 그룹의 인터뷰 대화(입력).
- `src/samples/무브온/deployment-discovery.json` — 대화에서 조립된 배포 결정 데이터(계약).
- `src/samples/무브온/deployment-brief.md` — 배포 계획서(고객 C레벨용 7섹션 exemplar).
- `src/samples/무브온/product-input.md` — 제품 인풋(본진 프로덕트팀용 exemplar).

또한 discovery 없이 `/alfboard:report`를 부르면, 새로 쓰지 않고 이 무브온 예시를 보여줄지 먼저 물어(데모 폴백) 처음 쓰는 사람이 한눈에 전체 흐름을 본다. 파일별 설명은 [`src/samples/README.md`](src/samples/README.md) 참조.

> 정량 수치(테스트·타이밍·샘플 금액)는 동봉 코드와 자동 테스트로 재현 가능하며, 채널톡 관련 수치·인용은 공개 자료(위 참고 URL) 기반이다. 미확인 항목은 쓰지 않았고, 확보 못 한 값은 미상으로 표기한다. 모든 산출물은 배포 담당자·프로덕트팀 검토용 초안이며, 실제 배포·계약 효력을 갖지 않는다.
