# product-input 작성 포맷 — 본진 프로덕트팀용 (고객 페인포인트/니즈 + 제품 고려사항)

> 두 번째 산출물 `product-input.md`를 집필할 때 따르는 포맷과 원칙 정본이다.
> 이 문서는 **PRD가 아니다.** 배포 담당자가 채널톡 본진 프로덕트팀에 올려보내는 "현장 신호 정리"다.

## 이 문서는 누구를 위한 무엇인가

- **받는 사람**: 채널톡 본진 프로덕트팀 — 알프 제품/로드맵 오너(지식, 규칙, 태스크 기획과 엔지니어링)
- **목적**: 이 배포에서 반복 관측된 고객 페인포인트와 니즈를 정리하고, 그것을 제품으로 만들 때 현장이 가르쳐준 고려사항을 함께 올린다
- **역할 경계**: 배포 담당자는 제품 오너가 아니다. 기능을 처방(스펙)하지 않는다. (1) 고객이 실제로 겪는 페인포인트와 니즈, (2) 만들 때 챙겨야 할 조건, 엣지케이스, 함정, 전제만 올려보낸다
- **집계 가치**: 한 고객은 신호이고, 여러 고객이 같은 것을 말하면 로드맵이다. 그래서 페인포인트와 니즈를 태그로 분류해 배포건끼리 쌓을 수 있게 한다

## A. 작성 원칙 (배포 계획서와 100% 공유)

`deployment-brief-format.md`의 A절 원칙을 그대로 따른다. 요약하면:

1. 두괄식 — 결론과 핵심 메시지를 문서와 각 섹션 맨 앞에.
2. 핵심 메시지 = 각 문단의 첫 문장. 각 섹션은 굵은 헤드 메시지로 시작.
3. 명사형 종결어미("~함 / ~필요 / ~구간임").
4. 문단의 마지막 문장에는 마침표를 찍지 않는다.
5. 근거는 상세하게 — 인터뷰 인용으로 뒷받침.
6. 문장은 짧게 끊어 읽기 쉽게. 만연체 금지.
7. 어려운 용어는 인라인으로 쉽게 풀거나 쉬운 말로 대체. 각주(`[^ ]`) 금지. 채널톡 통용어(알프, AICC)는 그대로.
8. 가운데점(`·`)을 쓰지 않는다. 쉼표나 "A와 B", 병렬 셋 이상은 `(1) (2) (3)` 넘버링.
9. 불렛은 `[짧은 라벨]`로 시작.

## B. 목차 (이 순서와 구조 고정)

```
# 채널톡 프로덕트팀 전달: {고객사} 배포에서 본 고객 페인포인트/니즈와 제품 고려사항
> 받는 사람, 목적, 근거(인터뷰 대상)

## 1. Summary
## 2. 고객 페인포인트/니즈 지도
## 3. 페인포인트/니즈별 상세
## 4. 제품 개발 간 고려사항
## 5. 확인 및 추적 필요사항
```

### 1. Summary
- 이 배포가 제품팀에 주는 **가장 중요한 메시지 1~2개**를 두괄식으로. 왜 지금 중요한지 한 문단으로 뒷받침한다.

### 2. 고객 페인포인트/니즈 지도
- 반복 관측된 페인포인트와 니즈를 **태그별 건수(신호 강도)**로 보여준다. 여러 그룹이 공통 지목한 것이 우선이다.
- 각 페인포인트를 **어느 제품 표면**에 걸리는지 표로 매핑한다(C절 어휘 사용).

### 3. 페인포인트/니즈별 상세 (근거 기반)
- 항목마다 `[라벨]`로 시작해 다음을 담는다:
  - **고객이 실제로 겪는 것** — 현재 알프가 어떻게 동작하고 어디서 막히나.
  - **현장 근거** — 인터뷰 인용과 빈도.
  - **제품 개발 시 고려사항** — 만들 때 챙겨야 할 조건, 엣지케이스, 함정, 전제. 스펙이 아니라 고려사항으로 쓴다.

### 4. 제품 개발 간 고려사항
- 여러 페인포인트를 가로지르는 고려사항(예: 지식 정비 없이는 어떤 기능도 성능이 안 남, 자동해결률 단독 지표의 함정, 개인정보 처리 전제).
- 이미 로드맵에 있는 것과의 관계(예: 알프v2 태스크가 이 방향을 이미 향하고 있음).

### 5. 확인 및 추적 필요사항
- 미확보 신호와 open questions.

## C. 제품 표면 어휘 + 태그 매핑

**제품 표면**(어느 기능 영역에 걸리나): 알프 지식, 알프 규칙, 알프 태스크, 알프 대화(되묻기/맥락), 이관/핸드오프, 보안/개인정보, 애널리틱스/리포팅, 지표/대시보드, 지식 저작/온보딩 도구, 미트(AI Phone)/채널, 다국어.

**태그 → 표면 (기본 매핑, discovery의 `product_gaps[].product_surface`로 확인)**:

| 태그 | 뜻 | 주로 걸리는 제품 표면 |
|---|---|---|
| `action_task` | 실제 처리(주문, 취소, 교환 등) | 알프 태스크 |
| `reask_context` | 되묻기/맥락 수집 | 알프 대화, 알프 규칙 |
| `knowledge_authoring` | 지식 저작 자동화 | 알프 지식, 지식 저작 도구 |
| `voc_distribution` | 상담 데이터 타부서 유통 | 애널리틱스/리포팅 |
| `metric_redefine` | 성과 지표 재정의 | 지표/대시보드 |
| `handoff_quality` | 사람 이관 품질/보안 | 이관/핸드오프, 보안 |
| `multilingual` | 다국어 | 다국어 |
| `small_team` | 소규모 팀 최적화 | 온보딩/템플릿 |

## D. 가드레일

- **증거 기반**: 모든 항목은 discovery 슬롯(특히 `product_gaps`, `bottlenecks`, `integration`, `metrics`)에서 나온다. 비어 있으면 "확인 필요"로 표기하고 상상하지 않는다.
- **처방 금지**: "이렇게 만들어라"가 아니라 "만들 때 이런 것을 고려해야 한다"로 쓴다.
- **집계 훅**: 태그를 유지해 다른 배포건과 쌓을 수 있게 한다.
